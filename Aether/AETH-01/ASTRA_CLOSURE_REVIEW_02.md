## 2. Scientific claim ceiling: K3 under attack

### A. Does CONSTRUCTED_CAPACITY still overstate activation?

**Yes if read alone; not if the repaired compound contract is obeyed.**
Fixture 2 installs only B.opcode. B's routing, field selection, payload and
energy were already supplied. Its legitimate claim is causation of activation,
not construction of the latent machine's configuration. The document now says

There is also a false-negative channel: an energy donor can enable a

helper classified the edge only CAUSAL_VALUE_CONSTRUCTION. This is consistent

### B. RECURSIVE_CONSTRUCTION versus recursive activation

Fixture 4 really demonstrates A activates B, B activates C, then C writes D.
It does NOT demonstrate recursively constructed routing/field configuration.
Both local edge interventions, their timing, and B/C rescues are now tested;
an A knockout alone is no longer the whole argument. The qualifier is
RECURSIVE_ACTIVATION_OF_PRECONFIGURED_MACHINERY.

There is a plausible future evidentiary failure, not just an unattractive name:
the document calls the ladder "ordered claim strength," while a fully wired
activation cascade receives tier 4 and source-set construction of opcode plus
routing receives tier 3. A tier-only count/export could truthfully count the
former under RECURSIVE_CONSTRUCTION while falsely suggesting that configuration
construction recurred. The present packet does not make that upgrade.

**Do not require a rename for R1.** Before scientific reporting, require an
atomic record of tier, mechanism, constructed fields, source set, scaffold,
origin and horizon, and forbid interpreting tier order as a total ordering
of configuration construction. An exporter must reject a missing qualifier;

## 4. Controller attack: reproduced R1 blockers

### B1. Negative visibility is being promoted to irreversible termination proof

P/runpod_api.py:219-224 maps GET 404 to None; 291-293 also accepts DELETE 404.
P/age_controller.py:557-573 swallows a DELETE exception and marks an ID
terminated when the following GET returns None. It need not have received
DELETE 204. Official v2 NotFoundError means "not found or is not accessible
to the caller" [W1], not solely "resource no longer exists."

**Executed offline falsifier:** use the existing controller test rig, deliver
its valid run-bound GPU receipt/result/log, make DELETE ineffective and raise,
then make GET invisible after deletion is attempted. Actual outcome:
**PASS, cleanup_status=CONFIRMED**, with pod_1 still in simulated live inventory.
Restore GET visibility and invoke recover: cleanup remains CONFIRMED; cumulative
DELETE count stays 1 and GET count stays 2. No further check is made because
finish_owned skips terminated_ids (age_controller.py:586-599).

This does not assume a malicious provider or require an impossible guarantee.
Access loss is within the documented 404 meaning. The bounded safe answer is
CLEANUP_UNRESOLVED, not invented positive evidence. An independently armed
cutoff may later delete the Pod; it cannot make this earlier PASS truthful.

**Minimum repair/falsifier:** preserve DELETE acknowledgement separately from
GET visibility; a failed/unknown DELETE plus ambiguous 404 must not confirm.
Keep provisional IDs recoverable and recheck prior negative-only confirmations.
Use owned TERMINATED or a documented positive deletion acknowledgement plus
independent corroboration under verified account scope; if evidence remains
ambiguous, remain loud/unresolved. Add the exact access-loss/visibility-return
regression, plus DELETE-204-but-still-RUNNING and EXITED cases. Do not interpret
an API observation as proof of settled billing; operator charge verification
remains a distinct obligation.

### B2. Ownership reconciliation is disabled on the successful-response path

adopt() sets reconciliation_required=False (P/age_controller.py:436-444).
cleanup() scans inventory only when that flag is true (607-627). The success
test explicitly expects no LIST (T/test_aeth01_age_controller.py:346).

**Executed offline falsifier:** a single POST yields a valid owned pod_1
response while a second exact-owned pod_2 exists. The controller returns
**PASS/CONFIRMED**, performs zero listings and leaves pod_2. The duplicate is
not merely similarly named: name, immutable image and env.AETH01_RUN_ID all
match. A provider-side duplicate is not established to occur in reality;
neither does the public contract give this controller an exactly-once
allocation guarantee. The requested duplicate-failure model is not covered
by ensuring only one client POST.

For an ambiguous create, another probe hid pod_2 for all three scans while
exposing pod_1. Result: **FAIL/CONFIRMED**, one billed duplicate left, three
listings. This is not false top-level PASS, but it falsely closes cleanup.
When no Pod is visible at all, the existing code correctly remains unresolved.
When both duplicates are visible, it deletes both and conservatively remains
unresolved. Partial-page failures also correctly preserve positive ownership.

**Minimum repair/falsifier:** always retain a run-wide reconciliation duty;
scan before final confirmation even on normal success, without delaying
known-ID deletion. Preserve every positive ID. Test a successful-response
duplicate, a duplicate appearing after the third scan, and a formerly
"terminated" ID reappearing. No finite polling count proves absence under
unbounded eventual consistency: keep reconciliation pending/loud and hand
the durable ownership predicate to the independent reaper. It must not
disarm on this controller's optimistic CONFIRMED. Provider observations and
the empirical consistency limit must be reported, not converted into certainty.

### B4. Important integration failures lose their distinguishing evidence

The transport safely retains a numeric ProviderError.status, but run() maps
every non-ControllerError to CONTROLLER_FAILED (age_controller.py:687-692).
No method/status history is journaled. In three executed offline create
failures, HTTP 401, HTTP 422 and transport failure (status None) each produced
the same CLEANUP_UNRESOLVED, reason=CONTROLLER_FAILED, empty artifacts and the
same diagnostic state shape. These failures need different operator actions.

Further, repeated proxy 404/502/503/504 all become None; a RUNNING Pod whose
artifact service never starts and a healthy service behind a failed proxy can
both time out with no artifacts. The service's own startup/supervision message
goes to container stderr, not canary.log. AGE has no independent provider-log
collection path (P/pod_service.py:275-285; P/runpod_api.py:302-308).

**Minimum repair/falsifier:** journal allowlisted operation/stage, numeric HTTP
status or local error category, last Pod status, artifact presence and elapsed
time. Never record raw env/headers/provider bodies or arbitrary exceptions.
Distinguish schema-decode failure from transport failure at least coarsely.
Require a bounded, documented provider/container diagnostic capture route
independent of this proxy (operator capture is acceptable for one supervised
R1), with no delay to deletion beyond the reserved deadline. Test that the
401/422/transport cases and service-not-started/proxy-unreachable cases leave
different evidence or an explicitly identified unavailable-evidence boundary.
This blocks R1's requested information-value gate, not its transition arithmetic.

deadline compatible with the present REST path was established. Do not rely
on old CLI examples, GraphQL input acceptance, EXITED, or an in-container timer.
