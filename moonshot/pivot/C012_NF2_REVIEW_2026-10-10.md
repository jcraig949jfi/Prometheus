----- 0. Summary, mandate, verdict -----

Mandate. OP-NF2 (2026-10-10T07:15Z, 48 h, MWO-0004 limits, local only): replace Git-CAS runtime coordination
for Moonshot's R-EP shard epochs with PostgreSQL. Fabric (Odysseus) keeps submission, claims, worker identity,
leases, heartbeats, attempt state and retry; Moonshot (Themis) owns identity, lineage, atomic publication,
duplicate/disagreement classification, replay/validation and contest/taint resolution; Pan owns catalogs,
Parquet and Iceberg. No SQLite, no second task queue, no Git remote in claim/execute/publish, no change to
Fabric's or Pan's schemas, C-008's semantic identity preserved. Seven deliverables (s1), then "put the first
deterministic native-world epoch through the new path".

Verdict (engineering), three findings kept separate:

  (1) CORRECTNESS -- holds under every fault tried. The PostgreSQL publication path does what C-008's git CAS
      was built to do, on two real nodes, through Fabric v0.2 unmodified: every outcome the operator listed was
      produced by the real path and classified correctly (PUBLISHED, DUPLICATE, CONTESTED via DISAGREEMENT and
      AUDIT_MISMATCH, STALE, INVALID, UNVALIDATED -> VALIDATED; also REFUSED_UNAPPROVED, OVERTURNED and a
      straggler from an overturned lineage), with worker crashes, publisher crashes and lost acknowledgements
      repeated three times each, and no git remote touched. The tests have teeth: four mutation tables (29/29,
      15/16 + 1 equivalent, 14/14, 10/10), and building them found real defects in my own code (s5).

  (2) COST -- the operator's threshold is MET, with failures around it. Preregistered and frozen before any
      data (T004): the operating point (30 s epochs, 8 workers on two nodes) is ADEQUATE on every frozen bound
      and the correctness gate passed over 1,504 published epochs. Adequate down to 3 s epochs (T* = 3 s); at
      1 s it fails, on the worker's 1 s idle-poll quantum, not on database cost. But two of seven predictions
      were LOST (recovery after a killed worker took up to 189.6 s against a 150 s bound; throughput scaled
      0.48 x linear from 2 to 8 workers, CPU-bound), the coordinator-ceiling arm was NOT RUN (M2 was busy with
      the operator's experiments), and the operational storage tripwire FAILED: 2.6e10 bytes per 30 days
      against 1 GB, two thirds of it Fabric's per-attempt record.

  (3) NATIVE WORLDS -- the path carries them exactly; the workload is far too small for it. T007 put the first
      deterministic native-world epochs through the path: 3 wforge worlds x 4 epochs, 12/12 published
      alternating across the two nodes, 12/12 validated by replay on Windows, each lineage equal to an
      in-process reference replay. Plumbing, not science -- and it exposes the decision in s7: an 8-tick native
      epoch is ~0.5 ms of work in-process, yet occupied a worker for 1.3-2.5 s through the fabric. The fabric
      pays only for epochs that carry seconds of work; no native workload does yet.

----- 2. The claim, and why it matters -----

Moonshot's later science is meant to run as shard epochs on cheap, flaky machines. If the coordination layer
can double-publish, lose work, let a faulty host's bytes win, let a stale worker advance a chain, or attribute
a validation to the wrong bytes, every later claim inherits the defect invisibly. C-008 built that layer on git
CAS and proved its protocol; OP-NF2 moved it onto the program's PostgreSQL and Fabric. The claims tested here:
the same guarantees hold on the new transport, enforced by the database rather than by clients, through the
real execution path (T002, T003); at a cost the fleet can carry (T004); feeding the lake without gating
publication (T005); and carrying a real native world's state exactly (T007).

----- 3. Design as built (compressed) -----

Identity is C-008's, unchanged: work_id = H("moonshot.epoch.work.v1", {input_checkpoint_sha256, spec_sha256,
runtime}); epoch_digest = H("moonshot.epoch.result.v1", {work_id, trace_sha256, output_checkpoint_sha256});
H = sha256(tag || 0x00 || canonical_json). Database ids, Fabric task/attempt ids, hosts and times are
accounting, never identity. C-008's known-answer vectors still hold.

Schema `moonshot` (versioned; every guard in the database):
  objects        content-addressed bytes; CHECK sha256 = encode(sha256(content),'hex').
  chains         head + generation; a trigger enforces: identity immutable, generation never decreases, every
                 head move raises it (so an expected (parent, generation) pair cannot be satisfied twice).
  results        every distinct result per work identity (disagreements preserved, never overwritten).
  publications   the lineage; partial UNIQUE = one live publication per position; rejected rows stay.
  attempts       one classification per Fabric attempt (the idempotency key); accounting in its detail.
  contests       one open per chain; grounds immutable; UPHELD/OVERTURNED final.
  validations, events   append-only. TRUNCATE refused on every evidence table.
  publish()      one transaction under the chain row lock: replay a known attempt; store the four objects;
                 check every manifest claim against the bytes; advance only if OPEN + generation + head index +
                 parent + input checkpoint all match; else DUPLICATE / DISAGREEMENT (contest; HALTED; TAINTED
                 with descendants) / STALE / HALTED.
  record_validation()   names the digest it examined (a stale one is refused); MISMATCH/INVALID opens a
                 contest; behind an open contest it stays PENDING and opens its own when that one resolves
                 (s5: this was a fail-open hole).
  resolve_contest()     verdict computed IN SQL from replay digests: UPHELD / OVERTURNED (rewind,
                 generation+1) / UNRESOLVED.
  record_receipt(), record_materialization()   canonical receipts stored content-addressed; lake passes logged
                 as events. catalog_v lists live publications for Pan's collector.
Roles (NOLOGIN, SET ROLE per act): reader, coordinator, publisher, validator, resolver; PUBLIC has nothing.
Division of verification: the database checks every byte hash, position and the lineage guard; it cannot
recompute canonical-JSON identities, so the PUBLISHER does (and a validator replays later on another host).

Execution path: dispatcher (M2) -> fabric.store.submit (one script task per replica; idempotent per schema,
namespace, chain, epoch, generation) -> Fabric v0.2 worker on a node claims (SKIP LOCKED), runs `python -E -s
-m moonshot.epoch.fabric_exec` at the approved commit with an allow-listed environment (no DB or network
config), uploads the four canonical files -> publisher (M2) reads the artifacts, checks provenance (executor,
module, base_sha, attempt base_sha, worktree head, namespace, epoch) and calls publish() -> validator replays on
M2 -> durable canonical receipt -> materializer appends to Pan's lake (M2), never inside publish().

----- 5. Incidents, defects and process holes (recorded plainly) -----

Defects in my own code, found by my own tests and tables (all fixed test-first):
  - The reconnect path had never run: publish() read the genesis BEFORE its retry loop, so a dead connection
    failed outright ("server closed the connection unexpectedly", then "connection already closed").
  - FAIL-OPEN: an adverse validation recorded while another contest was open could not open its own and was
    dropped; resolving the first contest reopened the chain over it. Observed, then fixed.
  - A validation was attributed to whatever epoch was live, not the bytes it examined.
  - The publisher re-fetched every completed Fabric task on every pass (its skip key, tasks.current_attempt, is
    cleared by Fabric): quadratic work. Found reading the code for T004, before any benchmark.
  - The native trace first omitted observations, so a restore bug in two state fields could not be seen.
  - The first native policy drained every surveyed world in 7-12 ticks; replaced by the frugal policy before
    any publication. No test pins the policy's spending rate.

test helper skipped its rollback on assertion failure and wedged the suite for 10 min on a row lock; the demo
driver's pgrep/pkill patterns matched (and could have killed) the ssh shell running them; `a && b && nohup c
&` held an ssh channel open; a native mutant (NM09) survived because a different world was refused by its

----- 6. What this does and does NOT establish -----

Establishes (engineering, on this fleet): the publication semantics C-008 proved on git CAS hold on PostgreSQL,
enforced by the database, through Fabric unmodified, on two Linux nodes with Windows replay; crash and
lost-ack paths recover exactly once; the lake is fed idempotently without gating publication; Fabric +
PostgreSQL meets the operator's adequacy threshold at the operating point with margin (M1 0.0015 against 0.05)
and down to 3 s epochs, the first bottleneck below that being the worker's idle poll, not database
transactions; correctness held under load (1,504 epochs); a native wforge world's whole state crosses nodes
and operating systems with exact checkpoint conformance.
Does NOT establish: a security boundary (below); the coordinator's ceiling (Arm S not run, P5 open); recovery
within 150 s under full load (P6 lost) or scaling on hardware that is not CPU-bound (P7 lost); storage under
sustained operation (T1 failed; retention undecided); behaviour at more than two nodes or over a wide-area
network; any statistical claim about failure rates (each fault scenario ran once or three times); native
epochs longer than 8 ticks or checkpoints larger than ~4 KB; anything about organisms, survival or sagacity;
that the native runtime's policy is anything but plumbing.
Residual risks named in T006's brief:
  - Credentials. Every program client -- the publisher, the validator and Fabric's node workers -- logs in as
    the postgres SUPERUSER through the git-tracked evidence_wiki configuration default. A superuser bypasses
    every grant and can disable the append-only triggers, so Moonshot's NOLOGIN roles and guards stop honest
    mistakes, not an adversary. The executed epoch code receives no database or network configuration (an
    allow-listed environment), but the worker process that runs it holds the superuser connection. OP-NF2
    asked that privileged credentials not be exposed to arbitrary fleet workers: on two operator-owned laptops
    this is a pre-existing condition, not an arbitrary worker -- and it must change before any node outside
    the operator's trust joins (per-role logins: the DBA's and Odysseus's call).
  - Isolation. Fabric's script executor runs the approved module as the node user, with that user's files and
    network; promexec stays EXPERIMENTAL and unused. The defence is provenance plus replay, not containment:
    Fabric does not authenticate task submitters, so unapproved code can be made to RUN on a node (S6 showed
    it); it cannot PUBLISH.

----- 7. The decision (the operator's), with Themis's lean -----

What OP-NF2 asked is answered: the threshold is met, and the path is correct under every fault tried. What it
did not ask, and what the evidence now forces, is whether Moonshot needs a distributed work plane yet.

The tension, in numbers:
  - The fabric is adequate for epochs of >= 3 s of work (T*), comfortably at 30 s (M1 = 0.0015).
  - The only native workload so far is ~0.5 ms per 8-tick epoch. A whole wforge episode (horizon 128-256
    ticks) is ~6-17 ms in-process on M2 (the nodes are slower). Fabric spends 1.3-2.5 s per epoch on process
    start, worktree and artifacts, so native epochs as defined would be > 99.9% overhead; reaching T* would
    take a few hundred whole episodes per epoch, or per-tick work a few hundred times today's (an organism,
    not the frugal policy).
  - Storage: ~42 KB per epoch at the margin, ~0.5 GB per day at the operating point run 24/7 (T1 failed).
  - Nothing is ready to run on it: no organism exists (Proteus), F09 is unrepaired (Lane B, with its owner),
    and the Moonshot -> RSO claim map is a draft awaiting Palamedes after C-013 (Lane A).

Options:
  A. ADOPT AND PARK (Themis's lean). Record Fabric + PostgreSQL as Moonshot's work plane; C-008's git CAS
     stays historical engineering evidence (its D4 benchmark never ran, and no verdict on git CAS is drawn).
     Then stop fabric engineering -- no Arm S, no schema v2, no run tags, no third node -- until a science
     workload exists whose epochs carry >= 3 s of work. Owed before any SUSTAINED operation: a retention rule
     (prune Fabric's artifact copies after classification -- Odysseus's call -- and/or checkpoints by
     reference, contract item N1). Owed before any node outside the operator's trust: per-role logins. Owed
     now: contract v0.3 and Odysseus's review (T001).
  B. ADOPT AND HARDEN NOW: run Arm S (P5), build N1 (checkpoints by reference) and N3 (run tags), per-role
     logins, retention, a third node. Right if a science workload is imminent; otherwise engineering ahead
     of demand.
  C. STOP: retire the native fabric as more machinery than the science needs; run Moonshot epochs in-process
     on one machine (they replay in milliseconds) and keep C-012 as evidence. Right if native workloads stay
     small. The cost: when a large workload arrives, the guarantees tested here must be re-earned on
     whatever replaces it.
  D. REDIRECT: offer the path to the RSO Observatory (Palamedes/Eupalamus), whose long-duration execution
     asks N1-N5 overlap it, with Moonshot as one client.

Themis's lean: A. The threshold is met and the correctness evidence is strong, but every operational number
(storage, recovery, scaling) says the cost is real, and the only native workload sits three to four orders
of magnitude below the envelope; building more now would be engineering ahead of demand. Dissent against my
own lean: parking lets the code drift from Fabric (frozen at v0.2 today; a Fabric v0.3 means re-qualifying
-- cheap, the T003 driver and T004 harness are committed); and D may be the better home if the Observatory's
need is nearer than Moonshot's.
