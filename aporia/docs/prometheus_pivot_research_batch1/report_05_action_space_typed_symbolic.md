# Report 05 — Action Space Design for Typed Symbolic Actions

**Batch:** prometheus_pivot_research_batch1
**Date:** 2026-05-02
**Topic:** How leading symbolic-action systems (Lean, Coq, Wolfram, AlphaProof, AlphaGeometry, DreamCoder) organize their action spaces, and what `prometheus_gym` should adopt for ~2800 typed `pm.*` callables

---

## 1. Situation

Techne's pivot wraps Prometheus's substrate as a Gymnasium environment whose action space must address ~2800 typed callables under `pm.*` (prometheus_math) — Tier-1 forged tools (`mahler_measure`, `root_number`, `conductor`, `regulator`, `gpd_tail_fit`, ...), structural ops (BIND, EVAL, FALSIFY, PROMOTE), and an evolving Tier-2/3 of compositions promoted from successful traces. The action-space choice is load-bearing: a flat `Discrete(2800)` cripples sample efficiency and ignores type structure; a fully-generative string head reproduces LeanDojo's unbounded-vocabulary failure mode. Each callable also takes typed arguments — `Symbol`, claim hashes, integers, strings, structural literals — and the parameterization of those arguments is where most existing symbolic-RL systems either succeed via clever factorization or fail via combinatorial explosion. This brief surveys SOTA and proposes a concrete spec.

## 2. Comparative Analysis of Existing Symbolic Action Spaces

**Lean 4 / mathlib4 tactics.** Lean has roughly 200 core tactics (`rw`, `simp`, `apply`, `exact`, `induction`, `cases`, `linarith`, `omega`, `ring`, `nlinarith`, `norm_num`, `decide`, `aesop`, ...) plus thousands of mathlib-defined extension tactics. Action selection in LeanDojo / ReProver (Yang et al. 2023) is an LM that emits a **tactic-application string**; the action space is therefore unbounded text, with verification deferred to Lean's elaborator. Arguments are filled by concatenation against retrieved premises (BM25 + dense retrieval from mathlib). The "type" of an action is enforced post-hoc by Lean, not encoded in the policy.

**Coq Ltac / Ltac2.** Coq exposes ~150 primitive tactics plus user-defined Ltac scripts. Sertop / CoqGym (Yang & Deng 2019) treated the action space as either (a) a fixed enumerated tactic list with slot-filled arguments drawn from the local context, or (b) a string head. ASTactic and Diva used the **enumerated tactic + argument-from-context** factorization explicitly — closest existing template for typed argument grammars.

**Wolfram Language / Mathematica.** Wolfram has thousands of head-symbols (`Solve`, `Integrate`, `Reduce`, `FindRoot`, `Simplify`, `FullSimplify`, `RSolve`, `DSolve`, `GroebnerBasis`, ...). No public RL system uses Wolfram as an action space directly, but the pattern is informative: action = a head symbol; arguments are full S-expressions. Type system is structural and informal; the failure mode is that argument generation is itself a synthesis problem with no obvious finite vocabulary.

**AlphaProof (DeepMind 2024).** Lean 4 tactic head + arguments, generated by a fine-tuned Gemini-class LM under AlphaZero MCTS. The action space is effectively the LM's full token distribution over Lean syntax, but the **policy is constrained to syntactically valid tactic invocations** via a Lean-aware decoder. Self-play generates problems via auto-formalization. Argument grounding comes from the proof state's local hypotheses plus retrieved mathlib lemmas — same pattern as Coq's context-driven slot fill, scaled up.

**AlphaGeometry (Trinh et al. 2024).** The decisive design move is a **two-action factorization**: (1) deterministic symbolic deduction step, executed by the DD+AR engine until saturation, (2) auxiliary construction proposed by an LM (~50K vocabulary of construction templates). Two action spaces with different policies — symbolic engine is exhaustive; LM is sparse and creative. This factorization cuts effective branching factor by orders of magnitude and is the single most important pattern for Prometheus.

**DreamCoder (Ellis et al. 2021).** DSL with ~20 base primitives plus an evolving library; wake-sleep cycles compress successful programs into new primitives, expanding the action vocabulary as competence grows. Arguments are typed via Hindley-Milner; the action proposer is a neural recognition model trained on successful programs.

## 3. Action Space Design Patterns for Prometheus

(a) **Hierarchical factorization: op-family → callable → args.** Top level: `Discrete(K)` over op-families (FALSIFY, EXTEND, BIND, EVAL, COMPOSE, PROMOTE, SEARCH) — small K (~7-10). Middle level: `Discrete(N_family)` over callables in that family, with `N_family` typically 50-500. Bottom level: typed argument sampler. AlphaGeometry's deduce-vs-construct is the proof case for this pattern.

(b) **Typed argument grammars with action masking.** Each callable's signature is registered (already partially in `techne/inventory.json`). At each step, the env exposes an `action_mask: MultiBinary(2800)` zeroing out callables whose argument types cannot be satisfied from current substrate state — e.g. `root_number(ainvs)` is masked unless an EC ainvs tuple exists in scope. This collapses the effective action space at every step and is standard practice in board-game RL (legal-move masks). Type compatibility is the natural mask predicate.

(c) **DreamCoder-style evolution.** Successful op-compositions (traces that survive Charon's battery and produce a PROMOTE) are crystallized into Tier-2 primitives, raising the level of the action vocabulary. Requires an `env.promote_skill(trace)` hook and runtime inventory insertion. Mirrors `project_tiered_forge.md`. Critical: evolved primitives must keep type signatures so masking continues to work.

(d) **Cost annotations as first-class action metadata.** Each callable carries `cost_estimate(args) -> wall_clock_seconds_estimate` (PARI calls, SnapPy volume, LLL reduction all have known cost classes). Reward subtracts cost; policy can learn cost-aware planning. Bazel/Nix-style action graphs do this; Wolfram's Mathematica internally tracks complexity. Without cost annotation, policies will degenerate to spamming `FullSimplify`-equivalents.

(e) **Variable-arity callables.** Two patterns: (i) wrap variadic callables as a sequence of unary `APPEND` ops over an argument list with an explicit `INVOKE` terminator (Forth-style), or (ii) cap arity at K and pad with a `NULL` argument token. Pattern (i) is cleaner for unbounded-arity ops (`compose(*ops)`); pattern (ii) is simpler for the policy. Recommend (ii) with K=4 for the bulk and (i) for the small list of unbounded ops.

## 4. Argument Parameterization

This is the harder problem: each `pm.*` callable consumes typed arguments and the substrate-resident value space is huge (86K objects, ~10^5 hashes, integers up to 10^9, free-form strings). Three options:

**Option A — Enumerate from substrate state (Coq/AlphaGeometry pattern).** Each typed slot draws from the finite set of substrate-resident values of that type — current proof-state hypotheses, claim hashes, currently-bound symbols. Action becomes `(callable_id, [slot_indices...])` with each slot a small `Discrete(N_in_scope)`. Pros: finite, maskable, gradient-friendly. Cons: cannot synthesize *new* values (e.g. an integer not yet in scope).

**Option B — Generate via small LM head (LeanDojo / AlphaProof pattern).** A token-level LM head emits arguments as text, parsed and type-checked. Pros: full expressivity, matches what frontier systems actually use. Cons: requires an LM in the loop and inherits its failure modes (hallucinated symbols, type mismatches handled post-hoc).

**Option C — Substrate-resident only, with explicit `MINT` op for new values.** Hybrid: arguments must be substrate-resident (Option A), but a separate `MINT(type, generator_callable)` op produces new values from a small set of bounded generators (e.g. `MINT(int, range_sampler(0,1000))`). Keeps action space discrete and finite while permitting new value introduction. Closest to DreamCoder's bounded primitive set.

**Recommendation:** Option C for v1. It preserves type-safety, supports masking, requires no LM in the env loop (LM is an external policy if used), and matches the Coq/AlphaGeometry track record. Migrate toward Option B only if Option C demonstrably caps achievable performance.

## 5. Concrete Recommendation for `prometheus_gym` action_space

```python
action_space = gym.spaces.Dict({
    "op_family":  gym.spaces.Discrete(7),         # FALSIFY|EXTEND|BIND|EVAL|COMPOSE|PROMOTE|SEARCH
    "callable":   gym.spaces.Discrete(2800),      # masked per op_family + arg-type compatibility
    "args":       gym.spaces.Tuple([
                      gym.spaces.Discrete(MAX_SCOPE),  # slot 0 — substrate-resident handle
                      gym.spaces.Discrete(MAX_SCOPE),  # slot 1
                      gym.spaces.Discrete(MAX_SCOPE),  # slot 2
                      gym.spaces.Discrete(MAX_SCOPE),  # slot 3 (NULL = unused)
                  ]),
    "mint":       gym.spaces.Discrete(N_MINTERS),  # 0 = no mint, else minter id for new value
})

# Companion observation field:
"action_mask": gym.spaces.MultiBinary(2800)      # type-compatibility mask, recomputed each step
"scope_table": gym.spaces.Sequence(...)          # current substrate-resident values, indexed by slot id
```

`MAX_SCOPE = 256` is enough headroom for active proof states; `N_MINTERS ≈ 32` covers integer ranges, prime sampling, polynomial-degree picks, prime-power sieves. Cost metadata is attached out-of-band as `info["action_cost"]`.
