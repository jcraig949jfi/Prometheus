## 2. THE ORACLE PROBLEM — stated now, because it scopes every branch

Campaign W featurises over the pair's **guaranteed overlap** `exact_terms`. That value is computed by
comparing `op(src)` against `tgt`. **A real query is one sequence with no partner and no operator, so
the window is not available at deployment.** The windowed path uses oracle information.

This is a scope constraint, not a bug, and it makes the branches **asymmetric**:

- **W3 KILL is decisive.** No deployable rule can know the overlap better than the oracle. If even the
  oracle window buys nothing, no windowing strategy can, and the X-line's negative is robust to the
  window artifact — the line closes on a measurement rather than on a doubt.
- **W1 ADVANCE is not decisive.** It would establish an *upper bound* only. It licenses "design and
  test a deployable variant", never "the window fix works".

**This campaign can definitively close the line and cannot definitively reopen it.** Recorded before
measurement so no result can be read as more than it is.

A deployable variant is **named but not tested**: per-candidate length matching over
`min(len(A), len(B))`, which uses lengths only. Strictly weaker than the oracle, and O(N) feature
computations per query instead of one lookup.

## 3. Two implementation facts that changed the pass-2 design

**(a) The raw block was never the problem, and fixing it at 20 keeps dimensionality constant.**
`sig_v2` returns **125 features regardless of input length** (verified at 12/20/24/32/40/45 terms);
only my variable-length raw block made the vector dimension vary (145–169 observed). And on
development, **0.0% of pairs have `exact_terms < 20`** — the 20-term raw block is *always* inside the
guaranteed overlap already. So pass 2 fixes the raw block at 20 and windows **only the V2 block**,
giving a constant 145 dimensions and isolating exactly the component that over-reads.

**(b) Unbucketed windowing is computationally infeasible, so the window is quantised — and that
weakens the oracle.** Retrieval requires query and candidates in one space, so candidates must be
featurised at the query's window. Per-query windows would need >12M V2 computations (500+ queries ×
25k pool). Quantising into four buckets needs 4 × 25k = 100k, about four minutes.

    bucket    pairs        bucket    pairs
     20–24      915         33–40      511
     25–32      455         41–45      619

**Disclosed against the campaign's own interest:** bucketing to the bucket's lower edge makes the
oracle *coarser*. W3's decisiveness weakens accordingly — from "no windowing can help" to **"no
windowing at this granularity can help"**. That is a real reduction in what a null licenses and it is
stated now rather than discovered in the write-up.
