## The finding that outlives the campaign: the gate was never resolvable

Development 119/125 and frozen 118/125 differ by **one pair**. That is not a generalisation failure
being detected — it is a threshold finer than the instrument measuring it.

    frozen 118/125 = 0.9440   SE 0.0206   95% CI [0.9037, 0.9843]
    dev    119/125 = 0.9520   SE 0.0191   95% CI [0.9145, 0.9895]

    distance from frozen to the gate:  0.006
    binomial SE at p = 0.95, n = 125:  0.0195

**The gate sits at one-third of a standard error from the observed value, deep inside the confidence
interval of both splits.** Neither the development pass nor the frozen failure carries information.
I set an entry gate my own benchmark cannot resolve, then spent two passes moving a number across
it. Both readings were noise.

**The transferable rule, and it is a gate on gates:** a threshold whose distance from the measured
value is smaller than that measurement's standard error is not a gate. Setting one requires a power
calculation *before* the threshold is chosen. For a 0.95 criterion, SE = 0.01 needs **475 pairs** and
SE = 0.005 needs **1,900** — against the 125 this benchmark carries.

## GATE_ELI5 — what would unblock this park

**What is stuck:** we built a test to check whether our sequence-fingerprints can find hidden
relationships, but the test only has 125 examples, which is too few to tell the difference between
"94% right" and "95% right" — the wobble from luck is bigger than the gap we were trying to measure.

**What would unstick it:** rebuild the benchmark with at least 500 verified pairs, ideally around
2,000, and pick the pass mark from a power calculation before looking at any result; the pair-finding
scan already hit its own cap at 150 per operator, so the pairs exist and only the scan depth and the
compute to enumerate them are needed.
