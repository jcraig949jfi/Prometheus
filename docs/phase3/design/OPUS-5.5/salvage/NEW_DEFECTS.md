## Proteus SplitMix64 keyed random streams (org-a; REBUILD)
Paths: proteus/foundry/prng.py
- derive keys on the parent's current state, so the same tag derived before and after a draw gives different streams. R0 must derive only from untouched roots.
- weighted() and unit() go through floats (prng.py:58-76). This is deterministic under IEEE-754, but R0 should use integers.
- It has no runner-side validator that refuses undeclared shared streams. REP-07 needs one.
- Skeptic (DOWNGRADE): The recommendation rests on two claims: the value is (a) the semantics and (b) the receipts. I opened the code and both claims fail. Only the generator core holds up. WHAT HOLDS. next_u64 (prng.py:39-44) is correct SplitMix64. My probe ran on a scratch copy, not the repository, and seed 1234567 reproduces Vigna's published five-output vector exactly. That is the ONLY real correctness evidence for the generator, and it comes from this probe, not from the seat. randbelow uses rejection sampling with no modulo bias (prng.py:49-57). The file is integer-only in its core and stdlib-only (hashlib). It is LF with eol=lf in git attributes, so there is no CRLF hazard. DEFECTS (each verified by the probe): (1) The key encoding is not injective, and the keyed part is exactly what REP-07 needs. seed_from (prng.py:19-30) joins typed parts with a bare b'\x00' separator and no length prefix, and encodes every type other than int or bytes as 's:'+str(p). Measured collisions: - seed_from('a\x00s:b') == seed_from('a','b') - seed_from(b'x\x00b:y') == seed_from(b'x',b'y') - seed_from(None) == seed_from('None') - seed_from((1,2)) == seed_from('(1, 2)') - seed_from(1.0) == seed_from('1.0') REP-07's test is a runner configuration validator over DECLARED keys. Two distinct declared key tuples can map to ONE stream, so the validator approves while the arms silently share a stream. That is REP-07's named fake passing. Compare prometheus/cosmos/hashing.py:119, which uses canonical JSON and raises on non-canonicalisable types. (2) The derive semantics are the hazard, not the asset. derive (prng.py:81-83) keys the child on the parent's mutable current state. The probe shows the same tag derived before and after one parent draw yields different children. A stream object carries only `state` (__slots__, prng.py:34) and no record of its key. So the validator cannot enumerate which streams exist, and ORG-08's provenance has no key to record. The cited consumer, v0_6/livekernel.py:42, derives from a freshly built throwaway root, so derive-without-advance carries no weight there: seed_from(..., L, T) alone gives the same parallel == serial property. Nothing in the API stops unkeyed seeding. Proteus's own test_mutation.py:33 seeds SplitMix64 from Python's process-salted hash(name), which is not replayable across processes. (3) All streams are shifts of one 2^64 Weyl sequence, because a single gamma is used (prng.py:40). The probe confirms stream(s+1000*gamma) == stream(s)[1000:1200]. Expected overlapping stream pairs are about n^2*L/2^64: about 0.05 for 1e6 streams of 1e6 draws, about 5.4 for 1e6 streams of 1e8 draws, and about 54 for 1e7 streams of 1e7 draws. On top of that, seeds are truncated to 64 bits, so seed collision alone has P about 2.7% at 1e9 derived streams. REP-07 encourages fine-grained keys (arm, world instance, organism), and the DGM targets tens of millions of instructions per second per core. Counter-based keyed generators with 128-bit keys (Philox or Threefry style, or a SplitMix finaliser over key plus counter) avoid this by construction, and they make snapshot equal to the counter. (4) The float and edge paths are wrong: - weighted() with all-zero weights silently returns items[-1]. With weights [-1,1] it always returns 'b' and raises nothing (prng.py:70-79). - Integer weights are accumulated in float, losing exactness above 2^53. - randbelow(n) for n > 2^64 computes a rejection limit of 0 and loops forever (prng.py:53-56). EVIDENCE QUALITY. The 'reviewed' claim is unsupported: - prng.py has one commit (20a523289, 2026-09-02) and was never revised. - No review document exists. The intake dossier only lists its line count. - proteus/tests contains NO unit test of prng.py. There is no known-answer vector, no derive test and no seed_from test; every hit is a USE. - The replay tests compare a run with itself under the same seed, so they would pass with any deterministic function. That is a control that cannot fail as evidence for the generator. - The cross-host receipts (v0_3, v0_4 .json.gz; v0_5 .json) are whole-pipeline digests, not PRNG-specific. They come from three x86-64 CPython hosts: Windows 11 py3.12.10, Windows py3.11, and a WSL2 Linux guest (py3.12.3, plausibly the same physical box). For arbitrary-precision Python ints with explicit masking, agreement is close to guaranteed. - The evidence R0 actually needs, Python reference versus compiled fast-kernel bit agreement (CMP-01), does not exist. - Decisively, every fix R0 needs (injective encoding, 128-bit keys, integer weighted) changes every stream. That invalidates the very receipts cited as the value. COUPLING. EXTRACT means 'made shared'. A shared RNG module imported by both the DGM kernel and its REP-02 reimplementation conflicts with REP-06's I2 rule ('disjoint import graph apart from the statistics library'). Streams should be supplied by R0 through an interface and specified so that each implementation can be written independently. So the value is a SPEC, which the evaluator's own honest note concedes ('rewriting 80 lines is equally cheap'). VERDICT. The need remains: REP-07, REP-01 and ORG-08 at slot R0, all SLICE. The implementation is inadequate in exactly the keyed part those requirements care about. REBUILD, cost S (well under 5M tokens), at R0: - counter-based keyed generator: draw_i = mix(key128, i) - injective canonical key encoding (length-prefixed typed fields; refuse unknown types) - streams carry their declared key tuple for the REP-07 validator and ORG-08 provenance - integer-only sampling - KAT vectors plus planted mutant variants that must diverge (the Aether test_golden_vectors.py pattern) - Python-versus-compiled differential test proteus/foundry/prng.py stays frozen in place only so historical Proteus rows still replay.   - weighted() uses builtin float sum (prng.py:72-80), a cross-CPython bit-identity hazard; use integer weights or math.fsum.
  - Skeptic (DOWNGRADE): seed_from is not injective (verified): seed_from('a\x00s:b') == seed_from('a','b'), and float, str, None and tuple parts all collapse through str() under the 's:' tag, so seed_from(1.0) == seed_from('1.0') (prng.py:19-30).
