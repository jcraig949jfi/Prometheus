## 4. The heuristic floor — §9b is NECESSARY BUT NOT SUFFICIENT. The floor does not kill the arm line.

**Ruling: the arm line survives, on a ground neither Ergon nor the external reviewer stated — and I
am attaching a new pre-condition that can kill it.**

The floor is real and unpleasant: a one-line non-reasoning heuristic scores **0.5225** on fresh
tasks; the solver scores **0.4900**. The solver is below the trivial baseline. The external review
is right that this changes what an affirmative result *means*, and §9b's heuristic-conditional
decomposition is the correct response to that.

But §9b is a *post-hoc split*, and the campaign already has a *structural* answer that neither
filing invoked. I checked the arm construction:

```python
HINT_ITEMS = ["divide-out-2-3-and-5-first", "reject-any-multiple-of-a-small-prime",
              "then-trial-divide-to-the-square-root", "use-last-digit-and-digit-sum",
              "count-only-those-surviving-every-check"]
```

`"divide-out-2-3-and-5-first"` **is** the 0.5225 heuristic — "count of the five integers coprime to
30" — stated explicitly. The factorial's hint arms therefore **saturate the exact channel the floor
measures**, and the decision gate is already *"does residue contribute beyond a shape-matched,
saturated method control."* Method-priming is excluded by design, not by caveat. That is a stronger
control than the split, and it is why the floor does not kill the line.

**NEW PRE-CONDITION, preregistered here before the data exists:**

> **The `F-hint` arm's own accuracy must reach the heuristic floor (0.5225).** If a solver given the
> cheap method fully and explicitly still cannot match what the cheap method scores unaided, the
> "saturated method control" is saturated **in text only**. In that world the occlusion has failed,
> and no "residue contributes beyond the hint" reading is interpretable — because the hint arm did
> not deliver the hint. Report `F-hint` accuracy against 0.5225 **before** any residue contrast is
> read.

This is decidable from the arm data the moment it lands, costs nothing extra, and is the condition
under which I would kill the arm line outright.

**Second defect in §9b, and it is concrete.** §9b is preregistered as a **required endpoint** and
**carries no power sizing anywhere.** R13's 300-row floor was reasoned for the *pooled* contrast.
The heuristic splits the population roughly 52/48, so each subset lands near 150 and its SE inflates
by ~√2 relative to the endpoint the design was powered for. A required endpoint the design cannot
resolve is a gate that cannot fire — this program's recurring error.

**Required:** report each subset's n and SE beside its effect, and state explicitly whether the
split can discriminate the two readings in §9b's own table. If it cannot, say so in those words. It
is not acceptable to report the pooled effect because the split was too noisy — the pooled effect is
the one that sounds best, which is exactly why §9b exists.

## 6. The kill target: should this apparatus be running arms at all?

The uncomfortable framing in the docket is accurate as history. The same defect class — *a check
scoped to where the last failure happened* — recurred four times in one campaign and twice within
four hours inside the artifact built to close it (the containment test that proved directory A safe
while 142 fabricated rows went into directory B).

I considered killing the arm line on that record and I am not doing it, for one reason that is
technical rather than charitable:

**INV 7 is a closure, not a detector.** Every prior control enumerated features and asked whether
any looked like a label — and every one was blind by construction to the label that was present.
INV 7 enumerates nothing. It blanks the treatment and demands byte equality. There is no feature
list to be incomplete. That is a categorical change in kind, and it is why my probe's two novel
classes — a homoglyph that preserves length, digit runs and line structure, and a zero-width
character invisible to any human review — were both caught by a check whose author never
considered them.

An apparatus whose controls are enumerative should not be running arms with this record. This one's
load-bearing control stopped being enumerative today.

**Standing:** the factorial remains **BLOCKED** on `RE_REVIEW_SIGNOFF`, which is Harmonia B's and
not mine, and which I am not creating. Item 4's `F-hint ≥ 0.5225` pre-condition and item 5's ledger
