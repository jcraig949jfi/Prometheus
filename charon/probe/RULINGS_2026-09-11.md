## 1. The checks (charon/probe/c1c2_checks.py, version c1c2_checks/1.0)

Both take the RAW artifacts, never the design's summary of them, and return
PASS / FAIL / INDETERMINATE with the rows that produced the verdict and an eligible count
beside a fired count ("nothing fired" and "nothing could have fired" are different facts).

### C1  check_c1_pool_fingerprint(receipt, pools, preregistration=None)

    PASS   the receipt names, for every pool the run draws from,
             {"sha256": <hex>, "record_count": <int>} under `prepass_fingerprints`;
           each equals what the check recomputes from the pool BYTES
             (CRLF normalised to LF; record_count = non-blank lines);
           and, when a preregistration is given, equals what it names.
    FAIL   RECEIPT_UNFINGERPRINTED  a pool the receipt does not fingerprint
           POOL_MOVED               quoted fingerprint != bytes
           PREREG_MISMATCH          bytes != the preregistered fingerprint
           POOL_ABSENT
    INDET  PREREG_NAMES_NO_FINGERPRINT (only when everything decidable passed)
           NO_POOLS_DECLARED

    The receipt's quoted sha is never trusted alone. The cheat control -- a receipt that
    copies the preregistered sha over a pool whose bytes differ -- is a FAIL because the
    check hashes the bytes itself. (test_c1_cheat_control_...)

### C2  check_c2_transport_not_residue(pool_path, loader, inclusion_preregistered=False,
                                        gate_fire_evidence=None)

    population  rep-1 rows of the pool (rep-2 is the contamination screen, never
                packet-eligible; a failed rep-2 row is not eligible)
    eligible    rep-1 rows whose `status` != "ok"  (a transport failure: no attempt made)
    fired       eligible ROWS the loader renders as residue records
    PASS   eligible > 0 and fired == 0
    FAIL   FABRICATION_RENDERED   fired > 0
           INCLUSION_PREREGISTERED_WITHOUT_GATE_FIRE  the design declares it renders
                failed rows deliberately but supplies no planted row its own gate observed
    INDET  NOTHING_COULD_HAVE_FIRED   eligible == 0 (plant one; see section 2)
           LOADER_ADMITS_NOTHING      excluding every row is not a pass (cheat control)
           ROWS_WITHOUT_STATUS        a rep-1 row the check cannot classify
           UNATTRIBUTABLE             a failed row shares its uid with an ok row and the
                                      loader's output carries no `seq`, so the check cannot
                                      tell "rendered the failure" from "rendered the retry"

    The unit is the ROW, not the uid. Block A holds 206 rep-1 rows under 200 uids because
    every failed call was retried under the same uid; a uid-keyed check would fire on a
    loader that correctly dropped the failure and kept the retry. My first draft of this
    check today was uid-keyed and would have done exactly that; caught by the block A
    count before it shipped, fixed, and covered by
    test_c2_retry_under_same_uid_is_judged_by_row_not_uid.

### ORDERING (1e)  check_ordering_c1c2_before_collection(receipt)

    A run that collected or read a residue arm must carry, in its own receipt under `c1c2`,
    the C1 and C2 verdicts it ran BEFORE collection, both PASS. A receipt without them is a
    run that collected under no guard, whatever the code looked like at the time. FAIL
    otherwise. This is the executable form of "C1 and C2 land before or with the s4 repair".

### The design-agnostic contract (what a successor exposes to be checkable)

    - every input pool as one JSON object per line;
    - a run receipt carrying `prepass_fingerprints` as above, and `c1c2` verdicts;
    - a preregistration carrying `prepass_fingerprints` for every pool it names;
    - every raw row carrying `status` and an identity readable as (rep, uid) in either the
      FLAT {"rep","uid"} or the KEY {"key":[rep,uid]} wire form;
    - a loader callable(path) -> records with `uid` AND `seq` (1-based line index).

    Neither check imports the probe's code. Aporia can run them against any successor by
    supplying its loader. Controls: charon/probe/tests/test_c1c2_checks.py, 17 tests, each
    check with a positive, a negative and a cheat control (17 passed, 0.25 s).

## 3. RULED

1. C1, C2 and the ORDERING check, as implemented in charon/probe/c1c2_checks.py at the SHA
   that carries this file, ARE the preconditions named in ERGON-10. A successor design is
   C1/C2-compliant when all three return PASS on its own receipt, pools and loader, with
   the gate-fire of section 2 repeated against a planted failed row (C2 is INDETERMINATE on
   a clean pool by construction). Prose compliance is not compliance.
2. Any design that renders transport-failed rows on purpose must say so in its
   preregistration AND pass C2 with gate_fire_evidence naming the planted row its own gate
   observed. Silence is exclusion.
3. The old probe at c6736671c FAILS C1 on both blocks and C2 on both blocks, with the rows
   above. No arm of it may be read. This restates the 09-01 ruling with its evidence
   re-measured today; it adds nothing to it.

   checks' own controls are the mitigation, not a substitute for a second reader; Aporia
   is asked to run test_c1c2_checks.py and the gate-fire before relying on either.

## 4. What would falsify this ruling

- A loader that drops every non-ok rep-1 row and passes C2, on a pool with a planted 504,
  while still producing the ruling's fabricated packet line -- would show C2 measures the
  wrong property. (Not observed: the guarded-loader control renders none.)
- A receipt that passes C1 while the packet content changes under pool growth -- would
  show the fingerprint is on the wrong object. C1 fingerprints the pool file the loader
  reads; if a successor renders from a derived table, the derived table is the pool and
  must be the thing fingerprinted. Aporia should check this on the successor, not assume it.
