1. THE THREE QUESTIONS
--------------------------------------------------------------------------------

Q1 -- WHAT EXACTLY IS sfe_entry_hash?

ANSWER: SFE `events.entry_hash` -- the hash-chain integrity anchor of ONE ROW
in the SFE EVENT LEDGER, specifically the event named by the (now required)
sfe_event_id. One semantic object, not "an SFE hash".

Decided from data, not field names:
  PEW prod fossil rows                                 5452
  match SFE events.entry_hash universe        5452/5452  (100.0%)
  match SFE artifacts.blob_hash                    0/5452  (0.0%)
  match SFE artifacts.artifact_id                  0/5452  (0.0%)
  match SFE foundry_events.entry_hash              0/5452  (0.0%)
  (sfe_event_id, sfe_entry_hash) pairs that
   actually EXIST in the live SFE ledger      5452/5452
So the established meaning was already unambiguous in the data; it is
preserved, not re-chosen. No producer disagreement was found.

THE HARD PART, stated plainly: worlds.head_hash CANNOT be excluded by shape.
All 283 live head_hash values ARE some event's entry_hash (head_hash names the
head event). blob_hash and artifact_id are ALSO "sha256:<64hex>". Structural
validation therefore cannot separate the four classes.

Resolution: the class is pinned by REQUIRING the paired sfe_event_id
(^evt_[0-9a-f]{16,32}$), which exists only in the event ledger. A producer
holding a blob_hash or artifact_id has no evt_ id to pair with it. This costs
nothing: 5452/5452 historical rows already carry sfe_event_id. PEW validates
CLASS + SHAPE only and holds no SFE client by design; the auditable check --
that the pair exists in SFE -- belongs to the investigator.

Q2 -- HOW DOES ORDINARY EVIDENCE BIND TO A FOSSIL ENCOUNTER?

ANSWER: ONE mechanism -- typed columns on the evidence row:
    ew.evidence.encounter_id  +  ew.evidence.encounter_run_id
    FOREIGN KEY (encounter_id, encounter_run_key)
      REFERENCES ew.fossil_encounters(encounter_id, run_key)
    (encounter_run_key is GENERATED ALWAYS AS coalesce(encounter_run_id,''))

  write     POST /api/v1/evidence  {..., encounter_id, encounter_run_id}
  forward   GET  /api/v1/provenance/evidence/{evidence_id}
  reverse   GET  /api/v1/fossil/encounters/{encounter_id}/evidence
  idempotency  evidence ids are content-addressed: an identical re-submit
               returns the SAME evidence_id and stores ONE row
  refusal      422 unknown_fossil_encounter:<id>@<run> -- nothing written

WHY NOT A RELATION (rejected, with reasons): encounter identity is a PAIR
since migration 006, but a relation row carries a single text dst_id, so
binding through relations would require an invented composite-string
convention -- explicitly forbidden by the directive -- and a new relation_type
would broaden the ontology. Typed columns need neither, and the foreign key
makes a bad binding impossible at the DATABASE level rather than by
convention. MATCH SIMPLE is deliberate: encounter_id NULL => not enforced, so
all 124 pre-existing unbound evidence rows stay valid and untouched.

Q3 -- IS MIGRATION 006 ACTUALLY LIVE?

ANSWER: YES, verified directly, not inferred from the file's existence:
  ew.fossil_encounters PK  = PRIMARY KEY (encounter_id, run_key)
  run_key                  = generated column, coalesce(run_id,'') STORED
  indexes present          idx_fossil_enc_{run,ep,players,anchor,world,ns}
  the running service      reports schema_version 4 and accepts/serves the
                           006 key shape (gate I, checked through health +
                           pg_constraint in the same run)
NOTE: PEW has no migration-tracking table by design -- migrations/*.sql are
idempotent (IF NOT EXISTS / guarded DO blocks) and re-run on apply. Live
schema, not a ledger, is the source of truth.
