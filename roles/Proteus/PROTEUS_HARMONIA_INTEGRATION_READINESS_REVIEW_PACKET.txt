5. REGISTRY DESIGN
--------------------------------------------------------------------

    THE REGISTRY DESCRIBES SPECIMENS. IT DOES NOT DEFINE PLAYER TYPES.

Schemas: `proteus.player_registry.v1`, `proteus.player_registry_entry.v1`.

An entry carries, and carries only:

    organism_id, lineage_id, generation
    manifest                      the immutable player, embedded verbatim
    identity                      manifest_schema_version, runtime_hash,
                                  grammar_hash, grammar_version, affordance_hash
    provenance                    source, foundry_identity, population_seed,
                                  index_in_population, derivation,
                                  generation_manifest_id
    resource_envelope             n_regs, tape_words, genome_words,
                                  genome_instructions, code_writable, persist,
                                  tick_budget, out_cap,
                                  max_state_footprint_words,
                                  persistent_state_words, max_ops_per_tick,
                                  max_output_values_per_channel_per_tick
    validation                    the authoritative validator's verdict
    extrinsic                     THE ONE OPEN NAMESPACE
    entry_id

THE IDENTITY RULE, WHICH IS THE LOAD-BEARING PART.
`entry_id = sha256(entry minus extrinsic minus entry_id)`. A consumer may write
phenotype, scores, encounters or anything else into `extrinsic` and NEITHER
`organism_id` NOR `entry_id` changes. Two tests assert it, and the smoke harness
re-checks it at runtime by writing a phenotype and a score and confirming
identity holds.

UNKNOWN IS FIRST-CLASS AND PERMANENT. Every specimen ships
`extrinsic.phenotype == "UNKNOWN"` and Proteus never writes another value. There
is no scoring step, no classification step and no deletion path anywhere in the
package, so the lifecycle generate -> score -> classify -> delete is not merely
discouraged, it is absent.

FAIL CLOSED. `RegistryError` is raised on: unknown schema version, missing
required field, unknown field in any CLOSED object, organism_id that is not the
hash of its own manifest, entry_id disagreeing with recomputation,
resource_envelope disagreeing with the manifest it describes, duplicate
organism_id, tampered registry_id, or a missing registry file.

UNKNOWN FIELDS ARE HANDLED DELIBERATELY, NOT ACCIDENTALLY. Every object is
CLOSED and rejects unrecognised keys by name, with the message saying which. The
single exception is `extrinsic`, which is declared OPEN in the code, in the
schema document, and in the handoff.

ONE SOURCE OF TRUTH. Manifest validity is decided by
`proteus.foundry.vm.validate_manifest` and nowhere else; the registry records
the verdict and never re-implements the rules. The JSON contract document is
DESCRIPTIVE, exactly as the pre-existing player-manifest schema is, and a test
asserts its required-field lists equal the Python constants so the two cannot
drift.

Zero is an OBSERVATION here, not an assumption: the counter exists and is

8. THE HARMONIA CONSUMER WORKFLOW
--------------------------------------------------------------------

    export PYTHONPATH=/path/to/Prometheus
    # Windows:  set PYTHONPATH=F:\Prometheus

    from proteus.integration import registry as R
    from proteus.foundry.vm import Player, Meter, validate_manifest
    from proteus.foundry.prng import SplitMix64
    from proteus.foundry.lineage import checkpoint, restore

    reg      = R.load_default()                 # A. enumerate/discover
    ids      = R.enumerate_ids(reg)
    manifest = R.get_manifest(reg, ids[0])      # B. obtain by organism_id
    validate_manifest(manifest)                 # C. validate (authoritative)
    env      = R.get_resource_envelope(reg, ids[0])   # K. limits BEFORE run
    p        = Player(manifest)                 # D. instantiate
    st       = p.fresh_state()                  # E. fresh state
    rng      = SplitMix64(my_seed)              # caller owns the RNG, always
    outs, status = p.run_tick(st, inputs, n_out, rng, meter=Meter())  # F. tick
    snap     = checkpoint(ids[0], st, encounter_id, tick)              # G.
    st2      = restore(snap)                                           # H.
    entry    = R.get_entry(reg, ids[0])         # J. provenance + identity

    # I. replay: same manifest + runtime + seed + inputs => identical outputs,
    #    statuses, final state and op counts.

`status` is `"halt" | "yield" | "budget"` -- an outcome, never an exception.
Output overflow beyond `out_cap` is dropped AND counted, not an error.
`tick_budget` is a ceiling a caller may lower and cannot raise.

16. EVERY FAILURE ENCOUNTERED DURING THIS PASS
--------------------------------------------------------------------

F1. MY OWN ANTI-TAXONOMY GUARD CAUGHT ME, AND IT WAS RIGHT TO.
    `test_no_semantic_taxonomy_anywhere_in_registry` scans the committed
    registry for authored player-type and merit vocabulary. On first run it
    FAILED, reporting "quality" and "garbage". Both came from my own explanatory
    prose inside the registry -- the selection rule said "no behavioural,
    phenotypic or quality filter", and the extrinsic note said UNKNOWN "does not
    mean garbage". The registry has no business editorialising, so the prose was
    reworded and the guard left strict. Weakening the test to accommodate my own
    wording would have disarmed the one mechanical defence against a taxonomy
    appearing later. Cost: one registry rebuild; registry_id changed from
    390a22676d93b4c6... to b15e0a7f5f2dcb99....

F2. A MALFORMED HEX LITERAL I WROTE AND ALMOST SHIPPED.
    The smoke harness contained `FIXTURE_SEED = 0x5C0PE if False else 0x5C09E`
    -- an artifact of typing a hex-like word. `0x5C0PE` is not valid Python and
    would have been a SyntaxError on first execution. Caught before the first
    run by reading the file back, and replaced with the plain constant.

F3. I GUESSED A PRIVATE ATTRIBUTE NAME INSTEAD OF READING IT.
    The checkpoint-continuation test needed the PRNG's internal position. I
    wrote `rng.s`; the actual attribute is `rng.state` (SplitMix64 uses
    `__slots__ = ("state",)`). Caught by reading prng.py before running. The
    lesson is small and repeated: I guessed at an interface I had not opened,
    in a file I could have read in two seconds.

F4. AN ERROR-TYPE INCONSISTENCY I FOUND AND DELIBERATELY DID NOT FIX.
    `restore()` raises `ValueError` on a runtime-hash mismatch but `KeyError` on
    a structurally malformed snapshot. Both FAIL CLOSED -- no consumer can
    proceed on bad data -- but the error type is not uniform, so a consumer must
    catch both. Fixing it means editing `proteus/foundry/lineage.py`, which is
    inside the V0.6 audit identity, and would force an identity transition for a
    cosmetic gain this pass has no authorisation to spend. Reported here and in
    the handoff instead of silently changing an audited file.

F5. NO OTHER FAILURES. The population built, validated and replayed on the first
    attempt; no specimen was rejected; no determinism check disagreed.

20. WHAT HARMONIA MUST KNOW BEFORE THE FIRST INTEGRATION TEST
--------------------------------------------------------------------

1.  Read `reg["source_qualification"]` once. It is the whole caveat, it travels
    with the data, and you never need V0.6 archaeology.

2.  Running these 64 frozen specimens is fine. BREEDING them is not qualified.
    If you mutate, do not call the result unbiased evolution.

3.  You own the RNG. The player can never seed its own randomness. For exact
    replay you must preserve your RNG position alongside any checkpoint --
    the checkpoint stores player state only.

4.  `status` is an outcome, not an error. `"budget"` means the organism used its
    tick allowance; it is not a failure. A silent organism is not broken. 54 of
    64 emitted nothing under the fixture and all of them are valid players.

5.  `tick_budget` is a ceiling you can lower and cannot raise. Read
    `resource_envelope` before scheduling; the numbers are hard bounds.

6.  Write your observations into `entry["extrinsic"]`. It is the one open
    namespace and nothing you put there can change any identity. Leave
    `phenotype` as UNKNOWN until you actually know something -- UNKNOWN is a
    permanent legitimate state, not a defect to be cleaned up.

7.  Do not ask Proteus what a player is good for. There is no such field, by
    design, and a test fails if one appears.

8.  Channel counts may vary per tick and per world. Players address channels by
    register value mod channel count, so a genome written against two channels
    runs unchanged against seven. The ABI is deliberately not specialised to any
    arena, present or future.

9.  Everything fails closed. If something is wrong you get an exception, not a
    plausible-looking result. Catch `ManifestError`, `RegistryError`, and both
    `ValueError` and `KeyError` around `restore` (see F4).
