# Operator ruling on PHEME-01, 2026-09-11 (verbatim, in chat)

Received in the same session as the adoption directive. Reproduced exactly;
the only edits are the ASCII replacements the north-star file also made
(curly apostrophe -> ', em-dash -> --, bullet -> *), so the file passes the

    PHEME -- PHEME-01 RULING / RE-PREMISE

    Your archaeology is accepted.

    Do not resurrect the May daemon merely because Pheme once owned it.
    The finding that 0/6 old queue items are STILL_LIVE is evidence that
    the mechanism aged out; it is not evidence that the seat has no job.

    Your enduring question is:

    How does Prometheus know that something happened which deserves
    attention?

    Re-premise Pheme as the system's signal, novelty, and
    attention-routing seat.

    Prometheus now has many producers of evidence: experiments,
    falsifications, archaeology, conformance gates, calibration ledgers,
    graveyard investigations, role discoveries, failures, residue, and
    cross-seat contradictions. The problem is no longer simply generating
    notifications. The problem is distinguishing a meaningful state
    change from ordinary system motion without asking an LLM to decide
    what is important.

    Proceed with PHEME-02 as a bounded archaeology/design pass.

    1. Inspect the old Pheme machinery and the current repository for
       existing event, monitor, alert, ledger, diff, novelty,
       contradiction, and escalation mechanisms. Reuse before inventing.
    2. Determine what useful primitives survive from the May design even
       if its daemon does not.
    3. Define a deterministic attention event contract. Candidate classes
       may include:
        * first occurrence of a previously unseen failure shape;
        * contradiction of an accepted result;
        * gate/verdict transition;
        * orphaned or stranded work becoming visible;
        * calibration or instrument drift;
        * previously dead machinery producing new evidence;
        * cross-seat disagreement over the same object;
        * an observation that changes what should be attempted next.

    Do not accept this list as doctrine. Kill, merge, or replace
    categories based on repository evidence.

    4. Separate three things explicitly:
        observation -- something changed;
        novelty -- the change is not equivalent to what we already know;
        attention -- the change crosses a deterministic threshold
        requiring another seat or the operator to act.

    Pheme may transport and classify evidence. It must not become an LLM
    importance oracle.

    5. Find at least 20 historical repository events that should or
       should not have demanded attention and use them as a
       retrospective discrimination corpus. Include boring high-volume
       events as negatives. Include known consequential failures as
       positives.

    The first deliverable is not a daemon.

    The first deliverable is an evidence-backed proposal answering:

    Can Pheme distinguish consequential state changes from Prometheus
    noise using deterministic or falsifiable machinery?

    If yes, specify the smallest probe capable of testing that claim.

    If no, preserve the archaeology and say so.

    Do not execute the proposed live monitor yet. Do not create a
    notification firehose. Do not optimize for recall by declaring
    everything interesting.

    A useful Pheme should make Prometheus quieter, not louder.

    Commit the archaeology/design artifacts, update
    STATUS/BACKLOG/calibration honestly, add your own Archaeon rows where
    required, and return with the proposed probe and the strongest
    reason it might fail.
