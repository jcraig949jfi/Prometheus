-----
0. SUMMARY
-----
Question: can a model that runs on one 16 GB card rewrite a function of THIS
program so that the program's own tests pass?
  - This is an uncontaminated benchmark: functions mined from the repository
    and scored by the repository's own tests.
  - It sits beside the public HumanEval+ numbers measured in PAN-33.

Answer:
  - Sometimes. The best configuration, qwen2.5-coder:14b, passes 59 of 142
    functions: pass@1 0.415, Wilson 95% [0.338, 0.498].
  - Every model scores 0.43-0.71 LOWER here than on HumanEval+ (P1 holds).
    The public benchmark overstates what these models do on this codebase
    by about half or more.
  - The top three configurations cannot be told apart:
      qwen2.5-coder:14b    0.415
      gpt-oss:20b@4096     0.373
      qwen3:8b             0.352
  - The HumanEval+ ranking did NOT transfer (P2 lost). gpt-oss:20b, tied
    first on HumanEval+, is last here at a 1024-token budget.
  - The budget is why. gpt-oss spends its tokens before writing code:
    104 empty answers of 142 at 1024 tokens, still 54 at 4096 (P3 holds:
    4096 > 1024 by 32 tasks to 0).
  - The pre-added 32B size arm could not be run on M2 without endangering
    the machine. It is reported as not run.

5. INCIDENTS (and what they validated)
-----
5.1 CHEAT failed before any model ran. A `pass` body satisfied 18/160 tests
  (tests that only check "does not raise"). Those 18 moved to the secondary
  set (A2) and a stricter CHEAT2 was frozen before running (7.0%, passes).
  The primary number therefore never counts a test a do-nothing body passes.
5.2 Size arm killed.
  - qwen2.5-coder:32b at num_ctx 8192 loaded at 22 GB on the 16 GB card and
    ran 35% on the CPU.
  - The model server took 14 GB of host RAM; M2 reached 89%, and the Claude
    Code harness stopped the run at about 23:05Z.
  - Pan stopped the leftover processes, unloaded the model, released both
    leases and closed the run FAILED (no row used). RAM was back to 44% by
    23:10Z.
  - A first cleanup command also terminated its own shell, because its
    command line matched the pattern it searched for. It was redone with a
    script that skips its own process tree.
  - Not rerun: the harness asked not to, and it is the operator's machine
    (Q-013).
5.3 Pan's own model blocked Pan's next run. After the reviewer run, Ollama
  kept qwen2.5-coder:14b resident (10 GB), so the GPU-idle gate refused
  qwen3:8b. The model was unloaded, and the reviewer runner now unloads its
  model.
5.4 Before running gpt-oss@4096, a load check showed 12 GB, 100% on the GPU.
  Even so, its server held 9.8 GB of host RAM for the whole run (peak RAM 75%,
  stable). This is worth knowing for anyone sharing M2.
5.5 P2 was lost on 2026-10-09 by the first three runs. It stayed lost; it was
  not reinterpreted.

7. WHAT THIS DOES AND DOES NOT ESTABLISH
-----
Does:
  - On this program's code, the best 16 GB-class local model rewrites about
    2 in 5 functions to pass their tests.
  - HumanEval+ overstates every model here by 0.43-0.71.
  - Budget-hungry reasoning models need large budgets to compete.
Does NOT:
  - separate the top three. A larger task set or several samples per task
    would be needed.
  - test anything but greedy decoding at one temperature, one prompt and
    one context size. gpt-oss with thinking enabled, or a bigger budget,
    could rank differently.
  - measure code quality beyond "the tests pass". 103 candidate functions
    were never seen by their tests, so the task set favours functions with
    tests.
  - answer P4 (does size help?). That needs ~14 GB of M2's RAM for 1-2 h
    (Q-013).
  - say much about the 61 tasks no model solved; diagnose output exists
    (DIAGNOSE_20261009T235239Z.json) but is exploratory.

-----
9. QUESTIONS FOR THE REVIEWER (written to resist agreement)
-----
  1. The task set keeps only functions whose own tests see them and that
     pass in a sandbox (160 functions mined from 1,381 test files). Does
     that select for easy, well-tested code, making even 0.415 optimistic?
  2. The masked-body prompt shows the whole module. Is that leakage (sibling
     functions show the style) or exactly the realistic setting?
  3. "empty response" for gpt-oss counts as a fail. Is that fair to a model
     whose thinking cannot be switched off, or should its budget scale with
     its overhead?
  4. Holm over 10 pairs at n = 142 has little power for differences < 0.1.
     Should the program fund more tasks before trusting any ranking among the
     top three?
  5. Is one sample per task (greedy) enough, when pass@k would show whether
     a model "can" vs "does" write the body?
