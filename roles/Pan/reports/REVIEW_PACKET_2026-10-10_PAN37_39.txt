-----
0. SUMMARY
-----
The operator wants platform code reviews done by the agents already at
work, with each reviewer's reliability MEASURED, not trusted (Q-011). Pan
built a calibration set:
  - 40 "seeded bugs": small mutations of the program's own functions, each
    kept only because the function's own test file catches it;
  - 20 clean functions;
  - frozen scoring: one finding per item; a hit is a line within +-2 of the
    bug.

Before scoring any reviewer, Pan measured what a reviewer scores WITHOUT
reading code. Verdict on set v1: UNFIT.
  - A regex that flags only lines containing `return None` or `not (`
    scored recall 0.45 with 1 false alarm in 20. That looks like a careful
    reviewer.
  - The frozen "unreliable" rule passed every non-reviewer tried.
  - 21 of 40 seeded bugs carried their mutation operator's text signature.

Set v2 was then built under rules frozen and pushed before generation.
Operators were changed to render like ordinary code; candidates leaving a
text tell are rejected; a four-part tell gate decides use. v2 passes the
gate: the regex now scores 0.025.

One property survives by design: the line with the most mutation sites
locates 70% of v2's bugs. Line location is cheap, so a reviewer is judged
on recall scaled by its false-alarm rate, not on recall alone.

-----
2. THE CLAIM AND WHY IT MATTERS
-----
Claim: on set v2, a reviewer's recall and false-alarm rate measure its
REVIEWING. Pattern-spotting on the generator's text and line-location
heuristics are bounded by measured floors that a reviewer must beat.
Why: without floors, a reviewer's 0.45 recall at a 5% false-alarm rate
would read as competent. On v1 a regex got exactly that. Weighting review
findings by a broken instrument would mislead every downstream decision.

-----
3. DESIGN AS EXECUTED
-----
3.1 Common to v1 and v2.
  - Source: the 142 primary tasks of PAN-34 (functions whose own test file
    sees them).
  - A mutant is kept only if its task's tests FAIL with it.
  - 40 mutants + 20 clean items from unused tasks, in shuffled order.
  - Reviewers get the function's code only: no path, no task id, no
    repository access (A1). Otherwise the clean original is one search
    away.
3.2 v1 operators: comparison flip, and/or flip, +/- flip, int literal n+1,
  `if T` -> `if not (T)`, `return X` -> `return None`.
3.3 v2 operators: the first four unchanged. `return None` dropped.
  negate_test inverts a test only in forms ordinary code uses: the
  complement of a single comparison, adding or removing a bare `not`. It
  never writes `not (...)`.
3.4 v2 mutation rule, applied before the kill check. Reject a candidate
  that (a) contains a v1 tell, or (b) INTRODUCES a syntax-shape bigram
  found in fewer than 10% of the other clean task functions. A shape
  bigram is a token pair with identifiers -> ID, numbers -> NUM and
  strings -> STR; keywords and operators are kept.
3.5 v2 tell gate (verdict USABLE only if all hold and >= 30 mutants):
  G1  no tell in any mutated segment;
  G2  surface-tell recall <= 0.10;
  G3  no rare introduced shape;
  G4  rare-bigram recall <= max(random line, site density) + 0.10.
3.6 v2 reviewer bar: a reviewer with false-alarm rate FA beats chance only
  if the lower end of its recall Wilson interval exceeds
  max over floors of R_floor x min(1, FA / FA_floor).

5. INCIDENTS (and what they validated)
-----
5.1 "Run the tests" is not a reviewer floor. Every mutant was kept BECAUSE
  its tests catch it, so a test-running reviewer scores 40/40 by
  construction. The calibration therefore measures prompt-only review,
  and says so.
5.2 The first G3 draft was blind. It flagged the line with the rarest
  raw-token bigram and scored 0.125 on v1, below the random floor; a
  syntax-shape rarity version scored 0.35.
  - Reason: `return None` is in 9 of 142 clean functions and `not (` in 5.
    They are tells only RELATIVE to mutants, which an unsupervised rarity
    test cannot see.
  - Replaced before generation by the operator-informed rule, which flags
    27/40 of v1's mutants (negate_if 10/10, return_none 10/11,
    cmp_flip 5/7).
  - Recorded in the v2 prereg itself.
5.3 Gate change for the build, recorded. The plan was to wait for M2's CPU
  to fall below 60%. It held at 60-93% for two hours under the operator's
  experiments, so the build ran with 2 workers at below-normal priority
  instead of 4 at normal priority.
5.4 The tell rule shifts the operator mix: bool_flip 1 -> 0, off_by_one
  9 -> 15. The set now over-represents literal and test-inversion bugs.

7. WHAT THIS DOES AND DOES NOT ESTABLISH
-----
Does:
  - v1 cannot calibrate reviewers. It is retired, and the record says why.
  - v2 carries no tell that Pan's four detectors can see, and its
    non-reviewer floors are known.
Does NOT:
  - prove v2 tell-free. A learned detector, such as a model fine-tuned on
    mutant/clean pairs, might find patterns these four miss. The gate is
    the detectors Pan thought of.
  - measure reviewers who run code or read the repository; those are
    out of scope (5.1, A1).
  - represent real bugs. These are single-token mutations that the tests
    already catch, which is the easy end of real defects.
  - have power for small differences. With 40 mutants, a Wilson interval
    is about +-0.15 wide at mid recall.
  - say anything about any reviewer yet. None has been scored; the first
    (a local model) waits for the GPU.

-----
9. QUESTIONS FOR THE REVIEWER (written to resist agreement)
-----
  1. Site density locates 70% of v2's bugs. Is +-2 lines too generous a hit
     window? Would an exact-line rule measure something better, or just
     something noisier?
  2. The tell rule threshold (10% of clean functions) was chosen by Pan
     before generation, without a sensitivity run. At 5% or 20%, would the
     set and its verdict differ much?
  3. Dropping return_none and bool_flip makes the set easier to keep
     tell-free but narrower. Does a narrower bug mix bias reviewers toward
     looking for literals and inverted tests?
  4. The reviewer bar uses the strongest floor scaled linearly by false-alarm
     rate (random abstention). Could a smarter non-reviewer (abstain on
     short functions, say) beat that line?
  5. Is a calibration set whose bugs the tests already catch the right
     instrument for reviews whose value is catching what tests miss?
