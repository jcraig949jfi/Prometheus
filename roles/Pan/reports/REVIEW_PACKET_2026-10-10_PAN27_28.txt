3. DESIGN AS EXECUTED
-----
3.1 Atlas copy.
  - Types: bigint, integer, double, boolean, text, text[] and timestamptz map
    to Arrow types; everything else (17 jsonb columns) is read as text.
  - Fingerprint per table: row count plus an order-free hash (the sum of
    per-row sha256 prefixes mod 2^64). It is computed on the rows read from
    Postgres and again on the rows read back from Iceberg.
  - The reading session must refuse an UPDATE; this is checked every pass.

3.2 Vectors.
  - The exact reference is M2's in-process float16 matrix of the same
    real[] values that the index casts to halfvec (also IEEE half
    precision). Before use, the matrix was checked fresh: 2,000 sampled
    rows, cosine with the database 1.0000 for every one.
  - Recall@10 = |HNSW top-10 intersect exact top-10| / 10, averaged over
    the queries.
  - "Query-style" vectors: text encoded with the query instruction, as
    search does. The set is the 62 frozen retrieval queries plus 438 chunk
    headings drawn at random (setseed 0.07).
  - All index work ran under the Fabric lease skullport:cpu8, held
    13:09-13:29Z.

    gate measured the easiest case.
  - It passed at 0.966 while real queries were at 0.659.

    new backend, and two answers vanished.

    in the code and the controls file.

8. DECISION / RECOMMENDATION (operator's call; Pan's lean)
-----
  a) Keep migration 013 and the default ef 200. Pan's lean: yes. The cost is
     about 100 MB more on M1 and about 10 ms per query.
  b) Make pg the default on M2 too (one search path everywhere), accepting
     about 2% recall loss? Pan's lean: no, while M2 has the lake. Exact
     search is the measured baseline for the retrieval verdicts.
  c) Who runs `pan atlas snapshot` after 2026-10-12? Pan's lean: Atlas,
     after each `harvest all`. It is one command and reads only.
  d) Q-007 (Pan's budget on M1): with 90 GB free on M1 C:, Pan's 10 GB cap
     is about 11% of the remaining space. The operator may want a lower cap
     or the F: drive (2.1 TB free) for the cluster.
  e) "Drop the HNSW indexes" is a valid answer if off-M2 vector search is not
     wanted. Rollback is DROP EXTENSION vector CASCADE (real[] stays).

-----
9. QUESTIONS FOR THE REVIEWER (written to resist agreement)
-----
  1. 438 of the 500 query-style vectors are chunk headings encoded as
     queries, not questions people asked. Is that close enough to real use
     to gate on, or does it flatter the index (headings resemble chunks)?
  2. The exact reference is float16 and so is halfvec. Could shared
     quantization hide a recall loss that a float32 reference would show?
  3. Is an order-free sum of hash prefixes (64 bits) strong enough to call
     a 143k-row copy "lossless", or should a sorted full-content hash be
     required?
  4. The snapshot trigger uses pg_stat_user_tables counters. They reset on
     a stats reset or a crash, which can only cause an extra copy, never a
     missed one -- or is there a case where they hide a change?
  5. Was raising the default ef after seeing the curve a tuning-on-the-test
     problem? The 62 frozen queries were part of the 500.
