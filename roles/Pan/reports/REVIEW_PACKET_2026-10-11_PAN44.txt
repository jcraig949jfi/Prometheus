-----
0. SUMMARY
-----
Mandate (Sagacity Foundation directive, 2026-10-11, section 5):
  - "a minimal local, read-only MCP prototype", after the foundation map and
    the negative-space evaluation (both done first);
  - wrap existing tested Pan operations: search, pivot, references,
    permitted Atlas fact lookup;
  - no network-facing service, no writes, no access to withheld or sealed
    data;
  - "demonstrate that returned records retain provenance and that
    unauthorized data is excluded";
  - "do not recreate Pan's retrieval system inside an MCP server".

Result:
  - A stdio JSON-RPC server (no socket, no port) exposes 4 tools. Each wraps
    one existing operation.
  - Every record carries provenance (store, path or key, blob/commit or
    harvest ids, access class).
  - 15/15 live controls PASS against two real server processes, generator
    and evaluator. Every exclusion control has a non-vacuity twin.
  - The official MCP Python SDK client (mcp 2.3.0) connects, negotiates
    2025-11-25 and uses all 4 tools.
  - Enforcement is application-level plus a server-side read-only session.
    It is NOT database least privilege: the program connects as superuser.
    Changing that is a production authorization question for the operator
    (Q-014).

-----
1. WHAT WAS BUILT
-----
Reuse first:
  - pivot.collect and links.refs were split out of the existing CLI
    functions. The CLIs print from them. CLI output on a 242-backlink path
    was byte-identical before and after the split.
  - New: atlas_snap.lookup, a literal case-insensitive lookup in 3 permitted
    Atlas tables (fact 41,784 rows, proposition 10, blind_spot 7), with
    provenance columns. Also a CLI command.
  - New: db.connect read-only mode. PAN_DB_READ_ONLY=1 sets the server-side
    default_transaction_read_only=on.

Tools (closed input schemas, additionalProperties false):
  pan_search    search.hybrid     query<=500 chars, k<=25, kind, seat
  pan_pivot     pivot.collect     path, k<=25
  pan_refs      links.refs        path, k<=50
  atlas_lookup  atlas_snap.lookup table in {fact, proposition, blind_spot},
                                  text<=200 chars (literal), k<=50

Response envelope:
  - tool, clearance, read_only, retrieved_at;
  - excluded counts: refused_rule, outside_clearance, uncatalogued,
    atlas_mentions_hidden_artifact;
  - result, whose records each carry provenance.
  A hidden path and a nonexistent path get the SAME answer (visible false,
  same note, no records), so there is no existence oracle in the content.

Why hand-rolled rather than the SDK: the mcp 2.3.0 package pulls in HTTP
server dependencies, and the protocol subset needed is small (initialize,
ping, tools/list, tools/call). The SDK is used as the CLIENT in a scratch
venv to check conformance; it is not a dependency of Pan.

-----
2. ENFORCEMENT LAYERS (order a request meets them)
-----
  1. Clearance is fixed at launch (PAN_CLEARANCE).
     - Only generator (default) or evaluator may launch.
     - Adjudicator, infrastructure or anything else makes the server exit 2
       before serving.
     - No argument can name a role.
  2. Access classes (migration 014). Every SQL path in the wrapped
     operations applies the clearance filter. At generator clearance,
     BURNED_HOLDOUT, EMBARGOED_OUTCOME and PRIVILEGED_CRITIQUE are invisible.
  3. REFUSE rules.
     - The 119 credential-shaped files stay in the catalog with their
       content purged.
     - The wrapped operations alone would still serve their path metadata.
     - The server drops them.
  4. Inheritance by mention. An Atlas row whose text mentions the path or
     basename of a hidden artifact is dropped. Measured: 0 rows today.
  5. Read-only session, checked at startup (the server refuses to start
     otherwise). The server writes nothing, caches nothing, and loads its
     encoder offline.

5. WHAT THIS DOES AND DOES NOT ESTABLISH
-----
DOES:
  - Pan's retrieval is reachable through a standard protocol by a standard
    client, read-only.
  - Records keep provenance.
  - A burned holdout reachable at evaluator clearance is not reachable at
    generator clearance through pivot or search, including prompt-text
    escalation. refs was tested against the credential-shaped path only; it
    shares pivot's filter but was not separately run against the burned file.
DOES NOT:
  - Least privilege.
    - The server is superuser underneath. RLS does not bind it, and no live
      table has RLS.
    - A bug in the filter code would leak.
    - The controls test through the server for this reason, but tests are
      not a proof.
  - True inheritance for Atlas. "Mentions a hidden path" is a heuristic. A
    fact derived from a hidden file without naming it would pass.
  - Constant-time answers. Hidden and nonexistent are identical in content,
    not necessarily in timing.
  - Caller authentication. The launching user chooses the clearance, within
    generator or evaluator.
  - Better retrieval. Hybrid R@10 is 0.765 (bar 0.80), inherited.

  CLI already serves every operation it wraps.

7. QUESTIONS FOR THE REVIEWER (written to resist agreement)
-----
  Q1  Is a superuser connection with a read-only default meaningfully
      "read-only"? A superuser can SET default_transaction_read_only=off.
      Only the absence of a code path stops it. Should the prototype have
      refused to exist until Q-014?
  Q2  The evaluator launch exists so the non-vacuity controls can run. Is
      offering evaluator clearance through MCP at all a mistake?
  Q3  Search exclusion was tested with ONE query built from the burned
      file's own text. Is one query enough to call exclusion demonstrated?
      What would an adversarial query set look like? (Nyx owns adversarial
      work.)
  Q4  Hand-rolled protocol code is a maintenance liability next to the
      official SDK. Is avoiding the SDK's HTTP dependencies worth it for a
      stdio-only server?
