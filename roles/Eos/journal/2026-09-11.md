## A defect found at boot, reported not fixed

`python -m comms sync Eos` failed with
`psycopg2.errors.UndefinedTable: relation "comms.messages" does not
exist`. The cause is not a missing schema; it is the wrong database.

    probe 1 (default resolver on M2):
      current_database=prometheus_fire  server=::1  port=5432
      schemas: ew, information_schema, public
    probe 2 (EW_DB_HOST=192.168.1.202, the M1 spine):
      current_database=prometheus_fire  server=192.168.1.202
      schemas: agora, analysis, archaeon, bus, charon_duckdb, comms,
               ew, kill, meta, noesis, public, results, sigma, signals,
               tensor, viv, viv_dev_*, xref, zeros

evidence_wiki/config.json ships `db_host: localhost`, so on M2 both the
Evidence Wiki resolver and comms (which uses it) silently address a
LOCAL fork that carries only the `ew` schema. Both databases are named
prometheus_fire. A seat that followed comms/README.md's first line --
`python -m comms init` -- would have created a second, empty inbox on
this machine and begun posting into it, and every symptom would have
read as "quiet queue". This is the base role's own case: verify the
property, never the label. Two stores with the same name are not the
same store.

Not fixed by this seat: evidence_wiki/ and comms/ are other lanes'
code, and the correct fix (a config.local.json on M2, a required
EW_DB_HOST, or a refusal when the expected schema is absent) is a
decision for the owners. Reported as EOS-24 and in the comms report to
Archaeon; Mnemosyne owns the substrate. Everything in this pass that
touched comms ran with EW_DB_HOST set to the M1 spine.
