# FR-002 -- Basin width predicts which primitive evolution selects (Ares falsifier never run)
State: SHARPENED. Cluster: A accessibility and discovery. Sources: H-D3-56 H-D3-57
Relations: narrower-than FR-001; related FR-083 FR-118; prior art PA_accessibility_landscape.md (items 1,3,4; P6; U4; s7)
Last reviewed: 2026-09-27 (first sharpening; basin-vs-peak confound CONFIRMED in the primary data; the proposed
  re-parameterisation falsifier was already demoted by Ares on 09-25; an existing arm, c3, already tested "arrival")

QUESTION -- In Ares's substrate, does the width of a carrier's viable parameter region -- rather than the payoff of the
first usable carrier, or the rate at which it arrives -- decide which carrier evolution recruits?

WHY IT MATTERS -- Ares offers it as a design rule for every substrate: "a supplied primitive is available when its viable
region is wide and its gradient flat" (ares/ARES_CYCLE2_REPORT.md s4.5@3f68be2b9). If it is really a payoff effect, the
rule is wrong and primitive design should target intermediate payoff instead (Lenski 2003, via the PA note).

EXISTING EVIDENCE
Measured (ares/runs/sweep_c2@1dde117f7, report@3f68be2b9):
- All three carriers suffice alone on W4: only_recur 10/10 at cap (median time-to-threshold 10 gens), only_plast 10/10
  (17.5), only_keep 9/10 (30, tail to 90). recheck.json clean scores for only_keep: 6/10 exactly 40.0. So the
  ENDPOINT payoff of an evolved genome is tied at the cap; the difference is speed.
- basin.json (hand-wired, one node): keep best 33.75 at 0.98, viable 3/25 values; recur best 40.00, viable 14/23,
  saturating. VERIFIED: recurrence has BOTH the wider basin AND the higher single-carrier peak. The "higher peak" for keep
  (33.75 vs 24.56, DESIGN_C2 s2) is one hand-wired point, recur at w=3.0 (basin.json fit[10]=24.5625). The PA note's
  P6 confound holds: in the only swept data, basin width and first-carrier payoff are collinear.
- Killed explanations: immediate gradient (P4, mean one-mutation change ~0); raw opportunity (8x keep subsidy did not
  flip the carrier; keep load-bearing 1/10).
- c3_keep_reachable (keep_mut_sigma 1.5): usable-keep creation 0.0231 > usable-recur 0.0173, yet keep load-bearing
  2/10 (prediction >= 3/10 lost). This arm already tested ARRIVAL (Schaper & Louis) and it did not suffice.
- DESCRIPTIVE READ, this pass (champion snapshots, every generation, JSON only): in c3 the champion carries a keep
  >= 0.94 in 8/10 lineages, it appears at or before the first |w|>=1 recurrent edge in 5 of the 8 lineages where both
  appear, and it persists 65-117 of 120 generations in 6 of them (the 0.98 clip absorbs upward mutations). Arrival and
  persistence were both delivered; load-bearing stayed 2/10. My recurrence detector is crude (it finds no |w|>=1
  recurrent edge in 3 c1_all lineages, one of them classed RECUR), so treat this as a pointer, not a count.
Proposed, not run: s7.1 re-parameterise keep as log(1/(1-keep)) -- DEMOTED by Ares's 2026-09-25 annotation (report tail;
roles/Ares/RESUME.md s6.1@3f68be2b9) because it moves where mutations land without widening the viable region. The
decisive test named there: ARM A decoupled leak v = keep*v + f (predict keep load-bearing >= 5/10), ARM B
re-parameterisation as control. Nyx measured the basin on an EVOLVED W4 ring: viable for gain scale >= 0.8 up to gain
106 (ARES_W4_READING_2026-09-25.md s7a@bf5073a91), so "wide recur basin" is no longer only hand-wired.

UNCERTAINTY -- ARM A changes keep's basin AND almost certainly its peak (decoupled loading removes the 33.75 ceiling), so
as specified it cannot separate basin from payoff either. Whether flatness (Wilke 2001; needs high mutation rate)
matters at all when arrival and persistence are already supplied (c3).

CHEAPEST DISCRIMINATOR -- Two steps, cheapest first.
(1) Read-only, 2-3 h, no runs: for the 20 c1_all and c3_keep_reachable snapshot series, mark each generation where a
keep >= 0.94 node lies on a cue -> output path (edges only) and log the champion's train fitness then and at the
first recurrent carrier. Cue-wired keep that persists and is displaced -> payoff of the first carrier (33.75 < 40) is
the live explanation; keep never cue-wired -> "functional arrival" was never delivered and c3 did not test arrival.
(2) Seconds of CPU, then ~1 h for 20-40 GA runs: before any GA, run the existing basin sweep under the ARM A rule and
record keep's peak and viable width. If the peak rises to the cap, add a payoff-matched cell (cap the decoupled keep's
input gain so its single-node peak stays 33.75 while the basin widens). keep wins >= 5/10 at the matched 33.75 peak ->
basin/shape beats payoff; keep wins only when its peak reaches 40 -> first-carrier payoff, and FR-001 should read
"intermediate payoff" as the lever. Add the Wilke 4x-mutation factor only if both cells are ambiguous (PA s7).
