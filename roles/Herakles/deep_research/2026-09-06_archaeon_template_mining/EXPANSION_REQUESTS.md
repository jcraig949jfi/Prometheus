## 38. The ability to specify and draw from a predefined distribution of distinct worlds (tasks) within a single specification.

**Raised by:** Meta-Learning

**Why:** Meta-learning methods explicitly optimize for fast adaptation across a variety of learning tasks, fundamentally requiring a meta-training phase on a broad task distribution and a meta-testing phase on held-out tasks. The bench currently restricts each specification to exactly one world (a single seed root), making it impossible to evaluate generalization across a diverse family of tasks.

**Smallest form:** A modification to the 'world' object to accept a 'seed_roots' array and a 'distribution_type' string, providing the executor with a structured set of multiple tasks to iterate over during training and testing.

**Also blocks:** Meta-Learning

**Evidence:** Model-Agnostic Meta-Learning (Finn et al. 2017) trains models such that a small number of gradient steps on a new, unseen task drawn from a broader distribution produces good generalization performance [cite: 9, 19].

## 39. The bench lacks a formal deduction engine capable of parsing symbolic logic clauses, maintaining a proof state, and applying valid inference rules to verify derivations.

**Raised by:** Automated Theorem Proving

**Why:** Automated Theorem Proving and Neural Proof Search both require navigating the tree-structured state space of logical entailment, where every state transition must be strictly verified against formal mathematical axioms. Neither a 1D scalar random walk nor a bitstring hash comparison can model a formal mathematical environment, as they lack the syntactic and semantic grounding to validate whether a proof step is logically sound.

**Smallest form:** An executor formal_prover.v0 taking expansion_limit and search_strategy, which attempts to close a predefined proof goal and adds a proof_found boolean field to the result.

**Also blocks:** Automated Theorem Proving, Proof Search

**Evidence:** Schulz's E Prover (2002) and Polu/Sutskever's GPT-f (2020) explicitly require an underlying formal environment (such as an equational superposition engine or the Metamath/Lean assistant) to validate the soundness of logical derivations at each step of the search [cite: 4, 5].

## 40. The bench lacks a logic resolution engine capable of performing unification to test if a candidate logical hypothesis entails a set of background facts and examples.

**Raised by:** Inductive Logic Programming

**Why:** Inductive Logic Programming algorithms induce explicit logical rules to satisfy declarative logical examples, meaning any evaluation must involve a Prolog-like interpreter resolving the generated clauses against a knowledge base. The existing executors operate exclusively on numerical arrays and bitstrings, offering no mechanism to represent Herbrand orderings or execute logical unification.

**Smallest form:** An executor metagol_induce.v0 taking max_clauses and metarule_set, which runs a predefined logic induction task against a static background knowledge base and adds an induction_success boolean field to the result.

**Also blocks:** Inductive Logic Programming

**Evidence:** Muggleton et al.'s 2015 introduction of the Metagol system establishes that ILP fundamentally operates by evaluating candidate logic programs through a meta-interpreter matching higher-order rules [cite: 6, 11].

## 41. The bench lacks an executor capable of interpreting structured candidate programs and evaluating them against a symbolic specification or bounded oracle to yield a pass/fail correctness verdict.

**Raised by:** Program Synthesis

**Why:** Both Program Synthesis and CEGIS fundamentally rely on generating structured code and testing it against a strict specification (via I/O examples or logical constraints), often receiving counterexamples in return. The current bench only offers a scalar score against a 1D walk or a hashed bitstring, which completely fails to provide the structural evaluation or constraint satisfaction feedback required to drive an inductive refinement process.

**Smallest form:** An executor bounded_synthesizer.v0 taking max_iterations and sketch_size, which executes a predefined symbolic synthesis task and adds a synthesis_success boolean field to the result.

**Also blocks:** Program Synthesis, Counterexample-Guided Inductive Synthesis (CEGIS)

**Evidence:** Armando Solar-Lezama's 2008 work on Sketching demonstrates that these fields function by interfacing a SAT-based inductive synthesizer with a bounded model checker to produce boolean verification outcomes and counterexamples [cite: 1, 2, 3].
