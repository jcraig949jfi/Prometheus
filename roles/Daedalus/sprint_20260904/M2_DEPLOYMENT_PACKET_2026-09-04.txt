--------------------------------------------------------------------------

HOW DOES THE WATCHDOG NOW DETECT CODE/SERVICE DRIFT?

  IT DOES NOT. The watchdog is UNCHANGED and remains HEALTH-ONLY. It probes
  /v2/version and relaunches only if that probe fails. It compares no commit,
  no schema, no capability. A stale-but-healthy daemon still satisfies it
  completely -- it did so again at 19:50:01 today, LastTaskResult 0.

  Drift detection lives entirely in integration/sfe_preflight.py, which is a
  GATE RUN BY A CALLER, not an automatic supervisor action.

WILL A FUTURE CODE CHANGE CAUSE A REDEPLOY/RESTART CONDITION?

  NO. Commit anything you like; the watchdog will keep the old build running
  indefinitely. Deployment remains a deliberate human/operator act.

  I CONSIDERED MAKING THE WATCHDOG DRIFT-AWARE AND DECIDED AGAINST IT, and
  this is a design judgement worth challenging: a watchdog that restarts the
  engine whenever HEAD moves would kill a running campaign because somebody
  committed a README. Auto-restart-on-drift converts a visible, gateable
  problem into a surprise mid-experiment outage. Drift belongs at
  experiment-start as a GATE, not in a supervisor as an ACTION. If the
  programme disagrees, the change is small -- but it should be a decision,
  not a default.

CAN IT DISTINGUISH healthy-current / healthy-stale / unhealthy?

  Watchdog:  NO. All three healthy-looking cases are identical to it; it sees
             only answered/unanswered.
  Preflight: YES. Four controls run live today, smallest safe set, service
             never destabilized:

    CONTROL                              RESULT
    healthy-current (live, strict)       PASS, exit 0
    healthy-stale (live, demand a
      requirement it cannot meet)        FAIL, exit 1, names the deficient
                                         field
    unhealthy (dead port 8812)           FAIL, exit 1, "service down,
                                         firewall, or wrong bind address"
    wrong cert (m1.crt vs M2 engine)     FAIL, exit 1, "TLS FAILURE, not a
                                         dead service (T18)"

  The pre-deploy run against the genuinely stale daemon
  (preflight_m2_before.json, exit 1, 4 hard failures) is the real-world
  negative control; the four above are the deliberate ones.
