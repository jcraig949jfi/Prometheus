4. THE ADAPTER CONTRACT
---------------------------------------------------------------------
Location: techne/lib/donors/

    from techne.lib import donors
    donors.registry           # {name: adapter class}
    donors.available()        # names whose donor actually imports here
    ad = donors.get("tensorly")

    ad.identity()             -> DonorIdentity(name, distribution,
                                 version, upstream, license,
                                 identity_evidence)
    ad.capabilities()         -> [DonorCapability(name, summary,
                                 deterministic, inputs, outputs)]
    ad.manifest()             -> JSON-serialisable description
    ad.propose(capability, payload, config=None, seed=None)
                              -> DonorArtifact

    art.provenance()          -> dict, small enough to store per row
    art.replay_seed()         -> minimum needed to re-run the call
    art.payload               -> the donor's actual output
    art.native_score          -> the donor's own score, or None
    art.native_selection_relation

THE LOAD-BEARING FIELD

Every adapter MUST declare `native_selection_relation`, a machine-
readable SelectionRelation with fields:

    kind        objective | ordering | constraint | none
    direction   maximize | minimize | satisfy | none
    over        what the relation ranks
    supplied_by donor | caller
    note        prose caveat

The base class refuses to define a subclass without it -- the check
runs at class-creation time, so an adapter missing the field cannot
reach the registry at all.

WHY. A donor arrives pre-committed to an objective. pyribs fills an
archive by an objective; tensorly minimises reconstruction error;
egglog's extraction minimises a cost model. If an experiment scores a
donor's output with a Prometheus metric Z while the donor already
ranked that output by Y, an apparent Z-result may be Y relabelled.
Recording Y lets an experiment be designed to BREAK it rather than
inherit it.

NONE is a legitimate value and must be stated, never left blank and
never fabricated for API uniformity. cvc5 and DisCoPy declare NONE.

STRICTNESS. Unknown config keys raise. A wrapper that drops a key
records a configuration that never took effect, which makes the
provenance record a false statement.

FAILURES. Donor failures raise DonorError carrying (donor, stage,
cause). They are never converted into a successful empty result,
because downstream that is indistinguishable from a genuine null.

LIMITATION: CP via ALS is deterministic ONLY with init='svd' and a

13. TENSOR PARITY -- NATIVE_EARNS_DISTINCT_ROLE
---------------------------------------------------------------------
Report: techne/donor_tensor_parity_2026-08-31.json
Run:    python -m techne.scripts.donor_tensor_parity

PREMISE CORRECTION FIRST. The assignment recorded, from a prior
inventory, that prometheus_math carries HAND-ROLLED CP and Tucker with
TT wrapped through quimb, in violation of Standing Order #1. Read at
source on 2026-08-31 that is not what is there:

  * prometheus_math/symbolic_tensor_decomp.py is ALREADY a pure
    tensorly wrapper. Lines 42-55: it raises ImportError without
    tensorly and routes every decomposition to
    tensorly.decomposition.{parafac,tucker,tensor_train}. There is NO
    hand-rolled CP or Tucker to supersede. What existed was a DEAD
    MODULE.

  * prometheus_math/tensor_train.py is a quimb wrapper and is NOT a
    duplicate. It computes TT BOND RANKS at a truncation cutoff,
    packaged with a fiber-shuffle null, for measuring cross-axis
    coupling. symbolic_tensor_decomp.tt_decompose computes a TT
    FACTORISATION at a requested rank. Different questions.

So the real question was: two independent TT implementations now
coexist -- do they agree on tensors whose bond ranks are known by
construction?

    fixture         shape       truth      quimb      tensorly   agree
    rank1_outer     [4,5,3]     [1,1]      [1,1]      [1,1]      yes
    rank2_sum       [4,5,3]     [2,2]      [2,2]      [2,2]      yes
    rank1_order4    [3,4,3,2]   [1,1,1]    [1,1,1]    [1,1,1]    yes
    random_dense    [3,4,3]     [3,3]      [3,3]      [3,3]      yes
    matrix_rank2    [6,5]       [2]        [2]        [2]        yes

5/5 agreement, and BOTH match ground truth on all five -- so two
implementations agreeing on a wrong answer is excluded.

CLASSIFICATION: NATIVE_EARNS_DISTINCT_ROLE. Neither supersedes the
other on correctness; they answer different questions and deleting
either removes a capability, not a duplicate.

NON-CLAIM: agreement between two implementations is a fact about the
implementations. Nothing here says any decomposition improves
reasoning, transfer or search.

PER-DONOR VERDICT -- all five NO_COMPATIBLE_CONSUMER:

  tensorly  emits real-valued factor matrices. No type-preserving map
            to variable-length discrete instruction sequences.
  pyribs    two blockers. (1) archive solutions are FIXED-LENGTH REAL
            vectors; genotypes are variable-length discrete tuples.
            (2) pyribs needs a behavioural descriptor and the D-5 slot
            has no notion of one -- choosing a behaviour space for
            programs IS the experiment.
  discopy   emits typed diagrams, not register-machine programs.
  cvc5      emits variable assignments. Its SyGuS front end could
            synthesise program-shaped output, but seeding the library
            from a COMPLETE DECISION PROCEDURE collapses the assay's
            conditional structure: D-5 measures findability F given
            existence E and reachability R.
  egglog    operates on algebraic terms. RM genotypes are imperative
            sequences with jumps (JNZ, SKZ, SKG), which are not
            equational terms. Making egglog rewrite them requires
            giving it RM semantics as a theory -- the deferred build.

NO optional adapter path was implemented, because every route required
either a bespoke encoder or a semantic widening of the assay. Section
14 of the brief forbids widening the consumer to make a donor look
useful, and that rule was followed rather than worked around.

WHAT WOULD BE COMPATIBLE: a donor whose NATIVE output is a program over
the same instruction set. That is exactly what the library-learning
families produce. Which makes the Family A vs Family B decision -- the
one held in section 12 -- the gate on any donor-to-D-5 circulation.
