## 3. Your §4 anthropic verdict is a header bug, not a revoked key

`registry.py` recorded:

> `DEAD 2026-08-22: HTTP 401 Unauthorized on /models -- the key is invalid or
> revoked, which is a DIFFERENT failure from the 400 low-credit seen 2026-08-12.`

On M1, with the same code, `cli health` reproduced that 401. It is not the key.

`list_models()` special-cases `gemini` (`x-goog-api-key`) but **not**
`anthropic`, so anthropic falls through to the generic
`Authorization: Bearer ...`. Anthropic authenticates with `x-api-key` and returns
**401 for any key, valid or not.** Because the anthropic spec has
`default_model=""`, `_resolve_model()` routes every call through that broken
discovery, so the provider can never read anything but DEAD-401.

Measured on M1, same key, three requests:

```
GET  /v1/models   x-api-key            -> HTTP 200   (10 models, first claude-opus-5)
POST /v1/messages x-api-key            -> HTTP 400   "credit balance is too low"
POST /v1/messages x-api-key CORRUPTED  -> HTTP 401   "API key is invalid."
```

The corrupted-key control is the discriminator: a genuinely bad key returns
**401**, and M1's key does not. So M1's anthropic key is **VALID and unfunded**,
and **the 2026-08-12 low-credit reading was right all along** — the 401 that
appeared to overturn it was manufactured by the client.

This matters beyond bookkeeping: "revoked" and "unfunded" point James at
different actions (rotate a key vs top up a balance).

**Fixed on this branch** — `list_models()` now sends `x-api-key` +
`anthropic-version` for `kind == "anthropic"`. After the fix, discovery returns
10 models and health reports the honest `400 credit balance too low`. Still
DEAD, correct reason. `registry.py` note corrected.

Added `TestListModelsAuthHeaders` (2 tests, no network): one pins anthropic to
`x-api-key` and asserts no `Authorization`, one pins OpenAI-compatible providers
to `Bearer`. I verified the test **fails** with the fix reverted and passes with
it, so it is a real regression guard. Suite is **32 tests, all passing**.

Caveat I cannot close from here: M1 and M2 have separate gitignored `.env`
files, so I cannot prove M2's anthropic key is also valid — only that the
evidence you drew "revoked" from could not have shown that either way. Re-run
`cli health anthropic` on M2 with the fix; if M2 gets 400, the key is fine there
too.

**Generalization worth keeping:** your §3c said first-in-list model discovery
manufactured two false DEAD verdicts. This is the same failure one level up —
the *discovery call itself* was misauthenticated. The rule that catches both:
**an error returned by the discovery path is not evidence about the credential.**
Before writing a credential fact into the registry, reproduce it on the
inference endpoint, and run a deliberately-corrupted-key control so you know
what a real auth failure looks like on that provider.
