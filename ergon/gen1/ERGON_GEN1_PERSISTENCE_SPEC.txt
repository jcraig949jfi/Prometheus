1. THE ARCHITECTURE, AND WHY IT MAKES PARITY STRUCTURAL
====================================================================

The recorder does not import, wrap, patch or subclass anything in
agent_d5_blind/learner/m1.py. It observes objects the frozen learner
ALREADY returns -- res['scored'], res['solver'] -- and the library list
the frozen driver ALREADY owns.

Consequence: admission, eviction, ordering, mutation, candidate
evaluation, library lookup, random draws, budget and timing-sensitive
search semantics are untouched BY CONSTRUCTION rather than by promise.

In replay_m1.replay_lineage, `recorder=None` is the ONLY difference
between persistence-off and persistence-on. They are not two functions
kept in sync; they are the same instructions. Section 4A parity is
therefore a property of the code, and the test measures the property it
names.

Parity is nevertheless MEASURED, because a claim that has never been
tested is not evidence.

2.1 A DEFECT THE GATE-FIRE DISCIPLINE CAUGHT, IN THIS INSTRUMENT

The first version of the leakage scan's vacuity guard counted the ROOT
node, so `seen == 1` for any input whatsoever. scan_oracle_leakage(None)
therefore returned a GREEN "no forbidden fields" verdict over a
non-record. It was written to enforce ATK-013 -- a lookup that finds zero
rows must raise, never return a renderable value -- and it violated
ATK-013 itself.

It was caught by test_leakage_scan_refuses_to_pass_vacuously, a test
written for exactly that class, before any record was scanned in anger.
Recorded because the check that fails is the only one that was ever
evidence.

4. SCHEMA (brief section 4D -- minimality)
====================================================================

Per task boundary:
  schema, run_id, lineage, policy, position, family, task_seed, nav_seed,
  library_before[hashes], library_before_size, admissions[], admission_count,
  evictions[hashes], eviction_count, library_after[hashes],
  library_after_size

Per admission:
  artifact_hash, genotype, length, admission_reason, source_score,
  behavior_fingerprint, readmission

Per terminal-library entry:
  position_in_library, artifact_hash, genotype

Minimality is enforced in both directions and tested: no field outside
the declared allowlist, and no declared field that is never populated. A
field that is always null is bloat just as surely as a field that is
undeclared.

ORACLE BOUNDARY (sections 4C and 13). Persisted rows carry only what the
learner itself computes: its own genotypes, the FastTask distance it
already computed in ctx.d, and the FastTask output fingerprint that
admissions() already used. Excluded, though all present in the oracle-side
evidence ledger: witness, wlen, stratum, reachability status, path_len,
solved, first_solve, domain_size. Enforced mechanically by a recursive
key scan over the whole record, tested against seven planted fields and
one nested one.

4.1 THE ONE FIELD IN SECTION 3'S LIST THAT WAS NOT CAPTURED

Section 3 asks for "usage count if naturally observable without changing
behavior". It is NOT naturally observable. The library is read at exactly
one site:

    extra_pool[rng.randrange(len(extra_pool))]     m1.py, in fresh()

Recording which entry was drawn requires a probe INSIDE the frozen search
core. A pure append-to-a-list observer there would consume no rng and
change no control flow, so it is admissible in principle -- but it
modifies frozen code, and it is therefore exactly what section 4A's
parity gate exists to adjudicate.

It is deliberately NOT in this deliverable. Precondition A is complete
without it, and a usage probe should be a separate, separately validated
step, so that if parity ever fails there is no ambiguity about which
change caused it. This matters because section 7's I2 policy depends on
usage -- see the 08-31 review packet, FINDING 3, which showed that usage
under a uniform draw is age-weighting rather than a utility signal.

8. THE MEASUREMENT THAT CHANGES THE FRAMING
====================================================================

No artifact in any lineage survived longer than 18 tasks. Tracing the
admission position of every artifact in each terminal library:

  lineage 0: terminal library spans admission positions 42..57
  lineage 1:                                            40..57
  lineage 2:                                            42..57
  lineage 3:                                            42..57
  lineage 4:                                            41..57

  memory depth ................ 16, 18, 16, 16, 17 tasks (mean 16.6 of 58)
  history absent at endpoint .. 69% - 72% (mean 71%)

Under the frozen I0 policy the library is a ROLLING WINDOW over roughly
the most recent 16 tasks. It is not an accumulation over 58. The
arithmetic is elementary once the trajectory exists -- 64 slots divided
by 4.03 admissions per task is 15.9 tasks -- and it was not visible
before, because the trajectory was not recorded.

D-5 flagged this qualitatively. Its note to a successor reads: "design
task ecologies where library content cannot saturate." Nothing quantified
the depth. This is the depth. It is a refinement of a known limitation,
not a new discovery, and it is reported as such.

Two consequences follow. Both are DISCLOSED FOR ADJUDICATION, not
asserted as reinterpretations of another agent's verdict, which is not
this seat's to rewrite.

  C1  The alien zero-shot arm (G7, P5 NOT ESTABLISHED, +5pp p=0.26) loads
      final_libraries/lineage_j.json -- the terminal library. That library
      contains artifacts from the last ~16 tasks only. G7 therefore
      measured transfer from a 16-task window, not from 58 tasks of
      development. Whether that changes G7's reading is Charon's and
      Aporia's call.

  C2  The shuffled-history arm (G9, retained 100%) is position-matched, so
      at each position BOTH arms hold a ~16-task window; the contrast is
      which tasks fill it. The comparison is real at window scale. What
      the design cannot detect is a developmental ordering effect at any
      scale LONGER than the window, because no such history is ever
      resident. "Developmental ORDER is not the mechanism" is therefore
      sound as measured, and bounded to ~16 tasks. The D-5 verdict's own
      successor note anticipates this remedy: ecologies where content
      cannot saturate.

8.1 A CORRECTION TO MY OWN CHARTER, FILED AGAINST MYSELF

My charter of 2026-08-30, section 4.1, states: "Every memory result in
Prometheus to date is an accumulation result... No experiment in this
repo has ever measured a DELETION... A memory system that cannot forget
is a log."

The narrow claim survives: no deletion was ever MEASURED, because the
trajectory was never persisted. The framing around it does not. D-5
executed approximately 843 evictions across 5 lineages (168.6 x 5) and
discarded 71% of its own developmental history before the endpoint was
read. D-5 forgets aggressively. It forgets by recency, blindly, and
without record.

So Gen-1's real contrast is not accumulation versus forgetting. It is
RECENCY-forgetting versus SELECTIVE-forgetting, at a cap that is already
binding for 43 of 58 tasks. That is a better-posed question than the one
I wrote into my own charter, and I would not have found the error without
persisting the trajectory the brief demanded first.

I am the conflicted party in both directions here and say so per standing
constraint: this correction makes Gen-1 look better-posed, which is the
outcome that keeps my own generation running.
