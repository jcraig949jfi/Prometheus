The brief requires persistence that does not alter admission, eviction,

DESIGN. The recorder does not import, wrap, patch or subclass anything

6. FINDING 1 -- THE LIBRARY IS A 16-TASK ROLLING WINDOW
====================================================================

This is the finding that changes the framing, and it was invisible
before the trajectory existed.

No artifact in any lineage survived longer than 18 tasks. Tracing the
admission position of every artifact in each terminal library:

  lineage 0: terminal library spans admission positions 42..57
  lineage 1:                                            40..57
  lineage 2:                                            42..57
  lineage 3:                                            42..57
  lineage 4:                                            41..57

  memory depth ............... 16, 18, 16, 16, 17 tasks (mean 16.6 of 58)
  history absent at endpoint . 69% - 72% (mean 71%)

The arithmetic is elementary once the trajectory exists: 64 slots
divided by 4.03 admissions per task is 15.9 tasks.

Under the frozen policy the library is a ROLLING RECENCY WINDOW over
roughly the last 16 tasks. It is not an accumulation over 58.

PRIOR ART, STATED SO THIS IS NOT OVERSOLD. D-5 flagged this
qualitatively. Its own note to a successor reads: "design task ecologies
where library content cannot saturate." Nothing quantified the depth.
This is the depth. It is a refinement of a known limitation, not a new
discovery, and it is reported as one.

TWO CONSEQUENCES, DISCLOSED FOR ADJUDICATION. These are not asserted as
reinterpretations of another agent's verdict, which is not this seat's
to rewrite.

  C1  The alien zero-shot arm (gate G7, claim P5 NOT ESTABLISHED, +5pp
      at p=0.26) loads final_libraries/lineage_j.json -- the TERMINAL
      library. That library holds artifacts from the last ~16 tasks
      only. G7 therefore measured transfer from a 16-task window, not
      from 58 tasks of development.

  C2  The shuffled-history arm (gate G9, retained 100% of the advantage)
      is position-matched, so at every position BOTH arms hold a ~16-task
      window and the contrast is which tasks fill it. The comparison is
      real AT WINDOW SCALE. What the design cannot detect is a
      developmental ordering effect at any scale LONGER than the window,
      because no such history is ever resident. "Developmental order is
      not the mechanism" is sound as measured, and bounded to ~16 tasks.

8.1 NOTHING VERIFIES THE FREEZE RECORD

anti_cheat/frozen_hashes.json records sha256 for 31 files across five
freeze points. anti_cheat/static_checks.py implements A1, A3 and A5 and
NEVER READS IT. No other code in the campaign reads it either.

8.2 THE RECORD IS BYTE-INOPERATIVE ON A WINDOWS CHECKOUT

18 of 31 entries fail a byte-level check here. SEVENTEEN are explained
entirely by core.autocrlf=true rewriting LF to CRLF on checkout. They
are not violations and nobody touched those files.

This is a trap worth generalizing: a byte-level freeze check on this
repo reports 17 false violations on any Windows machine, and a check
that cries wolf 17 times gets switched off. Future freeze records should
hash LINE-ENDING-NORMALIZED content. The validator shipped with this
finding normalizes, then asks git which revision the content matches,
which SEPARATES the two confounds instead of estimating between them.

8.3 ONE GENUINE POST-FREEZE EDIT: THE ANTI-CHEAT SCRIPT ITSELF

After normalization exactly one mismatch survives:

  anti_cheat/static_checks.py
    frozen hash matches commit ... 1c68630da  (Phase 1 apparatus)
    edited after the freeze in ... b503c5cfd  (INTERIM EVIDENCE: G4 PASS
                                               +10.95pp)

The file was changed in the same commit that reported the headline
result. The diff adds an exemption to its own oracle-field scan:

    HARNESS_EXEMPT = {'run_arm.py'}
    ...

        continue

This is the defect class this campaign is named for -- a check that
removes a region before inspecting it -- arriving in another agent's
codebase. It is why the file was inspected.

ASSESSMENT, LARGELY EXCULPATORY. The exemption is documented in the diff

Two residuals a reviewer should still weigh:

9.1 THE FIX THAT WAS REFUSED

Adding the fingerprint made the oracle-leakage scan FAIL, with two hits.
One pinned source is 'exact_oracle/oracle.py', and as a dict KEY that
correctly trips a scan matching forbidden substrings in field names.

The cheap fix is to exempt the fingerprint block from the scan. That is
precisely the defect filed against D-5 in section 8.3 -- exempting a
region before inspecting it -- and it was refused on those grounds, one
hour after filing it against someone else.

The fix taken changes the DATA SHAPE instead: frozen_sources became a
list of {path, sha} records, so the path is a VALUE rather than a field
name. The scan remains unexempted and still inspects every one of 6098
nodes.

This is recorded rather than quietly fixed because the two options are
OBSERVATIONALLY IDENTICAL in the certificate: both produce a green C.
The only thing separating them is which one is taken when nobody is
checking.

BOUNDARY, STATED EXPLICITLY: this did NOT discharge Charon's C1. That
condition is about ergon/probe's residue pool. The LESSON was applied to
a different instrument. The probe's C1 and C2 remain open and still
block collection there.

10. TWO DEFECTS CAUGHT IN THIS SEAT'S OWN INSTRUMENT
====================================================================

Reported because an instrument report listing only successes
misrepresents how the instrument was built.

10.1 A VACUITY GUARD THAT VIOLATED THE RULE IT ENFORCED

The first version of the leakage scan's vacuity guard counted the ROOT
node, so seen==1 for any input whatsoever. scan_oracle_leakage(None)
therefore returned a GREEN "no forbidden fields" verdict over a
non-record. It was written to enforce ATK-013 -- a lookup that finds
zero rows must raise, never return a renderable value -- and it violated
ATK-013 itself.

Caught by test_leakage_scan_refuses_to_pass_vacuously, a test written
for exactly that class, before any real record was scanned. The guard
now checks record SHAPE first and requires descent beyond the root.
